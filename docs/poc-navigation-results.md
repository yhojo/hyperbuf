# Project navigation PoC 結果

状態: **結果報告・決定済み** — 実施日 2026-10-08。ブランチ: `poc/navigation`(`7e5c692`、`113dfc1`)。§7 の方針をユーザーと合意(2026-10-08)。

## 1. 目的と範囲

README の「Project-oriented reading」(ファイル一覧、ファイル名検索、全文検索、多数ファイルでの応答性)と「Development-workflow integration」(外部更新の再読み込み)を、決定済みのシェル(SwiftUI + WKWebView)とレンダリング層の上で検証した。

検証用のコーパスは、`poc/bench/gen-corpus.py` で生成した(固定シード、リポジトリ外に配置)。

| コーパス | ファイル数 | ディレクトリ数 | サイズ |
| --- | --- | --- | --- |
| 1k | 1,000 | 50 | 2.5 MB |
| 5k | 5,000 | 250 | 12.7 MB |

各文書は見出し・段落・リスト・コード・表・他の文書へのリンクを含む。検索の検証用に、頻度の異なる語を仕込んだ(高頻度 `buffer`、中頻度 `reference`、低頻度 `zyxwv-rare-N`、日本語 `ハイパーバッファ`)。

実装したもの(PoC):
- **全文検索:** Swift の自前実装(並列走査、ASCII のみ大文字小文字を畳み込む部分文字列検索)と、ripgrep(外部プロセス)を、同じ `host.search` の契約で切り替えられるようにした。
- **ファイル監視:** FSEvents(旧: 0.5 秒ごとの更新日時の比較)。
- **ファイル名のあいまい絞り込み**(`fuzzy.js`)。
- **検索結果の仮想 buffer**(`*search: …*`)と、**行アンカー**(`path#line:N`)。

計測はすべて release ビルド、WKWebView 上(`window.hyperbufHost` 経由なので、IPC と JSON 変換の時間を含む)。

## 2. 結果の要約

- **5,000 ファイル(12.7 MB)でも、全文検索は約 46〜140 ms、ファイル名の絞り込みは 1 ms 以下、変更の検知は約 12 ms。** 操作の応答性は、この規模で問題ない。
- **全文検索は、Swift 自前実装と ripgrep のどちらも実用的。** 速度の差は小さく、機能・同梱・権限の面で選ぶことになる(§5)。
- **FSEvents は、旧実装(ポーリング)より桁違いに速く、削除も検知できる。** 採用が妥当。
- **仮想 buffer と行アンカーは、既存の操作モデル(履歴、Back/Forward、リンク)にそのまま乗った。**
- **課題:** Rendering PoC のバンドルを入れたことで、メモリが約 173 MB から約 380〜410 MB に増えた(§4)。

## 3. 性能

### 一覧・検索

`firstMs` は初回、`median` は 7 回の中央値。単位は ms。

| 操作 | 1,000 ファイル | 5,000 ファイル |
| --- | --- | --- |
| 一覧の取得(初回 / 中央値) | 19 / 10 | 53 / 31 |
| 全文検索 Swift: 低頻度の語 | 15 | 69 |
| 全文検索 Swift: 日本語 | 14 | 69 |
| 全文検索 Swift: 中頻度(218 / 983 件) | 15 | 70 |
| 全文検索 Swift: 高頻度(2,863 / 14,403 件) | 15 | 71 |
| 全文検索 Swift: 該当なし | 14 | 69 |
| 全文検索 ripgrep: 低頻度の語 | 13 | 47 |
| 全文検索 ripgrep: 日本語 | 14 | 47 |
| 全文検索 ripgrep: 中頻度 | 17 | 56 |
| 全文検索 ripgrep: 高頻度 | 34 | 140 |
| 全文検索 ripgrep: 該当なし | 16 | 46 |

- Swift の内訳(5,000 ファイル): ファイル一覧の列挙が約 29 ms、走査が約 39 ms。**列挙が時間の約 4 割を占める**ため、FSEvents で更新するファイル一覧のキャッシュを持てば、約 40 ms に縮められる(未実装)。
- 該当数にかかわらず Swift の時間はほぼ一定(1 ファイルあたり最大 3 行で打ち切るため)。ripgrep は該当が多いほど遅くなる(プロセスの出力の受け渡しと解析のため)。

### ファイル名のあいまい絞り込み(5,000 ファイル)

6 種の問い合わせ(1 語、複数語、飛び飛びの一致、該当なし)すべてで、中央値が **1 ms 以下**。1 打鍵ごとに全候補を再評価しても問題ない。

### ファイル変更の検知(5,000 ファイル、10 回の単発 + 1,000 ファイルの一斉作成)

| 方式 | 単発の更新(中央値 / 最大) | 一斉作成(1,000 ファイル)の通知 | 削除の検知 |
| --- | --- | --- | --- |
| FSEvents | **12 ms / 13 ms** | 全 1,000 件を書き込み開始から 113 ms で通知 | できる(1,000 件) |
| ポーリング(0.5 秒) | 364 ms / 381 ms | 全 1,000 件を 395 ms で通知 | **できない**(0 件) |

ポーリングは、ファイル数に比例して一覧の列挙コストも毎回かかる(5,000 ファイルで約 29 ms)。

### 検索結果の仮想 buffer

「buffer」で 500 件(上限)を表示するまで約 214 ms(検索 + 描画 42 ms)。検索結果のリンクから `path#line:N` で該当行付近へジャンプできることを確認した(文書の末尾付近では、スクロールの上限により、対象が画面の最上部ではなく画面内に入る)。

## 4. メモリ

アプリ本体と、新規に起動した WebKit のヘルパープロセスの合計(起動後 8 秒、release)。

| 構成 | 合計 |
| --- | --- |
| Interaction PoC(最小の描画) | 約 173 MB |
| Rendering PoC 以降(小さなサンプル) | 約 384 MB |
| 同 + 1,000 ファイルのプロジェクト | 約 407 MB |
| 同 + 5,000 ファイルのプロジェクト | 約 382 MB |

- **ファイル数にはほぼ依存しない**(ファイル一覧は Swift 側に持ち、JS には開いた文書しか載らないため)。
- **増加の原因は、描画バンドル**(WebContent プロセスが約 80 MB から約 290 MB に増加)と見られる。starry-night の文法と WASM、KaTeX、unified 群の読み込みが候補だが、内訳は未調査。

## 5. 全文検索の方式: Swift 自前 / ripgrep

| 観点 | Swift 自前(並列走査) | ripgrep(外部プロセス) |
| --- | --- | --- |
| 速度(5,000 ファイル) | 約 70 ms 一定(列挙 29 + 走査 39)。キャッシュで約 40 ms にできる | 約 46〜140 ms(該当が多いほど遅い) |
| 同梱・配布 | 不要 | 実体の同梱が必要(署名・公証の対象になる) |
| 権限・セキュリティ | 追加なし | 外部コマンドの実行権限の設計が必要(README のセキュリティ方針)。クエリは引数に渡さない |
| 機能 | 現状は部分一致のみ(ASCII の大文字小文字を畳み込む)。正規表現は未実装 | 正規表現、`.gitignore` などの除外、豊富なオプション |
| 実装の保守 | 自前のコードが増える | 既存の成熟した実装 |

実装中に見つけた落とし穴: **`Process` の引数は、ファイルシステム表現に変換されて、濃点・半濁点つきの文字(パ、バ など)が分解される。** 本文(合成済み)と一致せず、日本語の検索が 0 件になった。ripgrep にクエリを標準入力(`-f -`)で渡すことで解消した。外部プロセスを使う場合は、日本語のテストが必須。

## 6. 見つけた問題・気づき

1. **`Process` の引数の Unicode 分解**(§5)。
2. **旧ポーリングは削除を検知できず、ファイル数に比例して重くなる。** FSEvents に置き換えた。
3. **FSEvents のパスはシンボリックリンク解決済みの絶対パス**で、ルートの解決(`resolvingSymlinksInPath`)をそろえる必要がある。
4. **ファイル一覧はホスト側が真実を持つのがよい。** JS 側はキャッシュを持たず、必要なときに問い合わせる(5,000 ファイルでも 30 ms 程度)。
5. **ファイル一覧の除外規則が未定。** 現状は隠しファイル・隠しディレクトリのみ除く。`node_modules` や `.gitignore` の扱いは未検証(ripgrep は既定で `.gitignore` に従う)。
6. **ローカル画像・リソースを仮想 buffer から参照しても、既存のリンク解決が動く。** 仮想 buffer のパス(`*search: …*`)にはディレクトリがないため、リンクがルートからの相対になる。
7. **あいまい絞り込みの順位付けは単純**で、一部の問い合わせでは期待と違う候補が先頭になる(例: 飛び飛びの一致 `g3d42`)。改善の余地はあるが、応答性には問題がない。

## 7. 決定

2026-10-08、ユーザーと合意。

1. **ファイル監視は FSEvents を採用する。** ポーリングは廃止する。
2. **全文検索は、Swift 自前実装から始める。** `host.search` の契約でエンジンを差し替え可能にしておき、正規表現や除外規則が必要になった時点で ripgrep の同梱を再評価する(その際は §5 の落とし穴に注意)。ファイル一覧のキャッシュ(FSEvents で更新)による高速化は、必要になった時点で行う。
3. **仮想 buffer と行アンカーを、操作モデルに取り込む。** `docs/interaction-model.md` §5b に追記した。
4. **メモリ使用量の調査は、プロジェクト後半で行う。** 現時点では、約 380〜410 MB の増加を許容する。比較対象として、Marked 2 のようなビューアも長時間使うと 1 GiB 以上になる例がある。リークの有無と内訳(どの部品が何 MB か)を、後半にまとめて確認する。
5. **一覧・検索の対象は、当面 `*.md` とディレクトリのみ。** `.gitignore` は解釈しない。既定の除外は、隠しファイル・隠しディレクトリと `node_modules`(パッケージごとの README.md が大量にあるため)。除外規則の設定機構は、必要になった時点で検討する。

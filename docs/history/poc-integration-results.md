# Integration PoC 結果(連携プロトコル)

状態: **結果報告・決定済み** — 実施日 2026-10-08〜09。ブランチ: `poc/integration`(`af5ddee`、`c03cd2c`)。現行の契約は [integration-protocol.md](../dev/integration-protocol.md)、逆方向の連携の現行仕様は [edit-location.md](../dev/edit-location.md)。ここには、そこに至るまでの検証と決定の経緯を残す。

## 1. 目的と範囲

`hyperbuf` CLI・Emacs 連携が、HyperBuf.app に「ファイル(と行・見出し)を指定して開く」ための共通の契約を、実機で検証した。あわせて、ビューアから編集位置へ戻る逆方向の連携の要件を整理した。

## 2. 伝送の方式の決定

最初の提案は、URL スキーム(`hyperbuf://open?...`)を「開く」の正規の表現とし、CLI は URL を組み立てて macOS の `open` に渡す薄いラッパーにする、というものだった。起動と受け渡しは macOS(Launch Services)に任せ、自前のソケットやデーモンは作らない、という方針である。

その後(2026-10-08)、配布が Developer ID 署名・公証の直接配布(サンドボックスなし、Mac App Store は対象外)と決まったため、**CLI・Emacs 連携の主経路を Unix ドメインソケット(IPC)にする**方針を加えた。URL スキームは、アプリの起動と、外部リンクからの「開く」のために残した。

### 2.1 合意事項(2026-10-08)

1. 伝送の方式は、まず URL スキームで進める。機能上・セキュリティ上の大きな問題が見つかった段階で、軌道修正(双方向の経路の追加など)を検討する。
2. 範囲外のファイルは、ミニバッファで確認し、承認したルートを「信頼するルート」に永続化する。トークン方式は、初版には入れない。
3. 範囲外のファイルは、**URL 経由もソケット経由も、同じく確認する**。
4. Emacs の標準は**直接ソケット**とし、設定で CLI 経由にも切り替えられるようにする。
5. 配布は、ある程度の品質になった段階で、オープンソースとして GitHub で公開する。ビルド済みパッケージは、Developer ID 署名と公証による直接配布で、サンドボックスなしを前提に設計する。ただし、権限の明示と最小化というセキュリティ方針は変わらない。

(2 と 3 の「範囲外」「信頼するルート」は、のちにプロジェクトという単位をなくしたため、許可パス・警告パスと記憶したパスに置き換わった。[file-access.md](../dev/file-access.md))

### 2.2 初版では扱わないとしたもの

- 標準入力からの表示(`git diff | hyperbuf -`)。
- ターミナルのハイパーリンク(OSC 8)など、他ツールとの相互運用の拡張。

### 2.3 代替案(採用しなかった)

CLI が、アプリのデータディレクトリにあるトークン(`0600`)を URL に付ける方式。トークンのない URL(Web 由来の可能性がある)は常に確認を要求し、あるものは範囲内を確認なしで開く。強い区別が可能になる一方、トークンの生成・更新・共有の設計が増えるため、初版には入れなかった。

## 3. URL スキームの実機確認(2026-10-08)

`.app` バンドル(`CFBundleURLTypes`)と bash の CLI 試作を作り、LaunchServices に登録して確認した(確認後、登録は解除済み)。

| 項目                           | 結果                                                                                                                                                                                   |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| URL スキームの登録と受け取り   | `hyperbuf://open?...` が実行中のアプリに届く                                                                                                                                           |
| **未起動からの起動と引き渡し** | 1 回の `open` で、起動・URL の受け取り・該当行(`line:30`)の表示まで完結。CLI の実行から表示完了まで約 1.1 秒(アプリの起動を含む)                                                       |
| 起動中のアプリへの転送         | CLI の実行から URL の受信まで約 100 ms、表示完了まで約 265〜290 ms(5 回)。試作の bash と python の起動コストを含む                                                                     |
| 見出しアンカー・行アンカー     | どちらも該当位置に移動する。履歴に積まれ、Back で元に戻れる                                                                                                                            |
| ウィンドウ                     | 要求を連続して送っても、可視ウィンドウは 1 つのまま(`Window` シーン + `AppDelegate` の `application(_:open:)` で受けた)                                                                |
| 不正な要求の拒否               | 相対パス、`.md` 以外、`..` を含むパス、未対応の `v`、`line` が数字でない、`anchor` が長すぎる、未知の操作(`hyperbuf://delete`)、存在しないファイル。いずれも拒否され、画面に理由が出る |

### 実装中に分かったこと

- SwiftUI の `WindowGroup` と `onOpenURL` の組み合わせは、URL ごとに新しいウィンドウを作ることが知られているため、`AppDelegate` で受ける構成にした(`WindowGroup` の側は、実際には試していない)。
- **ページの準備ができる前に届いた要求を保持し、準備後に渡す必要がある。** 起動直後に URL が届くため(`ready` の合図を使った)。
- 外部(CLI)の `hyperbuf://` と、WKWebView 内部のカスタムスキーム(`hyperbuf://app/...`)は、同名でも衝突しなかった。

## 4. ソケット(IPC)の実機確認(2026-10-08)

Swift のサーバー(POSIX ソケット)と Python のクライアント試作で確認した。LaunchServices への登録は使っていない(アプリはパス指定で起動)。

| 項目                     | 結果                                                                                                                                                                                                                                                                            |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **権限**                 | ディレクトリ `drwx------`、ソケット `srw-------`(`bind` の時点から `umask` で 0600)                                                                                                                                                                                             |
| **コールドスタート**     | 未起動の状態から、CLI がアプリを起動し、ソケットの出現を待って、最初の `ping` が通るまで約 650 ms(2 回目は約 310 ms)。URL スキームで該当行を表示するまでの約 1.1 秒より速い                                                                                                     |
| **往復の遅延**           | 同一接続での `ping` は、中央値 0.04 ms / p95 0.07 ms / 最大 0.24 ms。接続→`ping`→切断も中央値 0.03 ms。`open`(描画まで含めて応答)は約 146 ms                                                                                                                                    |
| **`open`(行指定)**       | 該当行(`line:30`)が表示され、履歴に積まれ、応答が返る                                                                                                                                                                                                                           |
| **`get-location`**       | 約 1 ms で、選択中の window の現在位置を返す(PoC では選択の代わりに現在位置)                                                                                                                                                                                                    |
| **異常系**               | 不正な JSON、未知の操作(`delete`)、未対応の `v`、`path` なし、相対パス、`..` を含むパス、`.md` 以外、存在しないファイル、不正な `line`。いずれも対応するエラーコード(`bad-request`、`unknown-op`、`unsupported-version`、`not-markdown`、`not-found`)で応答し、アプリは落ちない |
| **範囲外ファイルの確認** | 確認待ちの間、応答が保留され、期限(`timeoutMs`、既定 30 秒)を超えると `timeout` で応答する(1.2 秒の期限で、1,259 ms 後に応答)。ミニバッファでの回答も確認済み(yes: 成功、no: `outside-project`)                                                                                 |
| **大きすぎる行**         | 2 MiB の 1 行は、接続を閉じる(エラー応答は届かない場合がある)                                                                                                                                                                                                                   |
| **パイプライン**         | 同一接続に連続して送った複数の要求に、すべて応答する                                                                                                                                                                                                                            |
| **並行**                 | 100 接続を同時に張って、100 件とも成功(15 ms)                                                                                                                                                                                                                                   |
| **古いソケットの回復**   | `kill -9` でソケットファイルが残っても、次の起動で、接続を試して応答がないことを確認して作り直し、約 310 ms で `ping` が通る                                                                                                                                                    |
| **二重起動**             | 2 つ目のプロセスは、既存のソケットに接続できることを検出する(`alreadyRunning`)。PoC では、検出後もウィンドウが残った                                                                                                                                                            |

範囲外ファイルの確認の回答の経路は、手動でも確認した。`--wait-ms 60000` で実行し、ミニバッファで `yes` と答えると `ok: true`、`no` と答えると `error.code: outside-project` で CLI に返る(待ち時間は、回答までの 8.5 秒と 2.2 秒)。

## 5. 逆方向の連携(ビューアから編集位置へ)の検討

### 5.1 背景

ユーザーの経験: 巨大な文書の記載ミスをビューアで見つけ、Emacs のインクリメンタルサーチで「該当箇所と思った場所」を修正したところ、**別の場所を修正してしまった。** 同じ文言が複数あり、見ていた位置と、検索で着いた位置が食い違っていた。この経験が、要件 R1〜R5([edit-location.md](../dev/edit-location.md) §2)の出発点である。

### 5.2 方式の比較

| 方式                                             | 内容                                                                                                         | 利点                                                                                                                              | 欠点                                                                                                                                                                |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. アプリがエディタを起動する(送り出し)          | ビューアのコマンドから、ユーザーが設定したコマンド(例: `emacsclient`)を実行する                              | ビューアの操作だけで完結する。多くのエディタに使える                                                                              | **外部コマンドの実行**(README のセキュリティ方針)。コマンド行や Lisp の式に値を埋め込むと、注入の危険。エディタ側での照合(R2・R3)には、結局エディタ側のコードが要る |
| B. エディタが取りに来る(引き取り)                | アプリが「現在の位置」を状態ファイル(アプリのデータディレクトリ、`0600`)に書き、Emacs のコマンドが読んで飛ぶ | アプリは外部コマンドを実行しない。**照合・強調・警告を、Emacs 側で完全に制御できる**(R2〜R4)。Emacs の利用者の操作(キー1つ)に合う | 利用者が Emacs 側で操作する必要がある。状態は更新時刻つきで、古いと分かるようにする(R3)                                                                             |
| C. エディタ固有の URL スキーム(`vscode://` など) | アプリが、エディタが登録した URL を開く                                                                      | 実装が簡単                                                                                                                        | 照合ができず、R2 を満たせない。エディタごとに異なる。Emacs には標準がない                                                                                           |

### 5.3 合意事項(2026-10-08)

1. **データの経路は B(エディタが取りに来る)を先に作る。** 外部コマンドの実行が要らず、R1〜R5 の照合を Emacs 側に置ける。Emacs のビルドに依存せず、ファイルを読めれば動く。
2. **「指している場所」は、マウスで選択し、右クリックメニューで示す。** カーソルは表示しない方針のまま、編集は頻度が高くないため、この手段で十分とした。メニューには、macOS 標準の項目(翻訳など)と同じ場所に「Edit in Emacs」を足す。
3. **R5: 曖昧なときは、ブロック全体への移動と警告にとどめ、推測で飛ばさない。**
4. **R3: ファイルが変わっていたときは、警告のみにする。続行する手段は設けない。** 何かが根本的におかしいことに、本人が気づいていないことが多いため、冷静に状況を判断する機会を与える。

その後、配布方式(サンドボックスなし)が決まったため、位置の問い合わせは、ソケットの `get-location` を第一候補にし、状態ファイルは代替とした。実装は `get-location` で行っている。

## 6. 実装(M4〜M6)で確定した点

仕様として残るものは [integration-protocol.md](../dev/integration-protocol.md) と [edit-location.md](../dev/edit-location.md) に取り込んだ。ここには、実装中の判断と確認の記録を残す。

- **サーバーの半クローズ:** クライアントが送信側を閉じても(半クローズ)、未応答の要求があるあいだは、接続を閉じない。同一の接続の複数の要求は、並行して処理され、応答は 1 回だけ書かれる。
- **ソケットの権限:** `umask` は使わない(プロセス全体の設定で、他のスレッドのファイル作成に影響する)。置き場所のディレクトリを先に 0700 にし、`bind` のあとに `chmod 0600` する。
- **`anchor` の長さ:** JSON Schema の `maxLength` と同じく、Unicode のコードポイントで数える(書記素ではない)。
- **Emacs 側の入力検証:** サーバーの規則と同じ検証を Emacs にも持つ(`hyperbuf--validate-open`)。規則がずれないよう、`protocol/examples/open-validation.json` を共有して適合テストをする(例を壊すと、Emacs のテストも失敗することを確認した)。URL の組み立ても `protocol/examples/url.json` で検証する。`url-hexify-string` は、予約文字と日本語を大文字の 16 進でパーセントエンコードするので、Swift 側の `URLComponents` が読める。
- **ネイティブの右クリックメニューの実機確認(2026-10-09、手動):** 位置の記録のみ(設定なし)と、`emacsclient` の呼び出し(設定あり)の両方で、期待どおりに動いた。メニューの項目が一番上に出る、選ぶと位置が記録される、Emacs が前面に出て移動する、曖昧な選択は `block`、未保存の編集・ファイル変更・検索結果は、移動せず警告、不正な設定は無視される。

## 7. 決定のまとめ

| 決定                                                   | 理由                                                                                 |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| 主経路は Unix ドメインソケット、URL は起動と外部リンク | 結果の応答・問い合わせ・確認の待ち合わせができる。往復が速い。Web 由来の要求が来ない |
| Emacs は直接ソケットが標準                             | プロセス起動のコストがなく、`get-location` の往復が速い                              |
| 逆方向の連携は、エディタが取りに来る方式               | 外部コマンドの実行が要らず、照合をエディタ側に置ける                                 |
| 照合に失敗したときは、続行手段を設けない               | 根本的な食い違いに、本人が気づいていないことが多いため                               |

## 1. 目的と範囲

HyperBuf.app の外から、**ファイル(と行・見出し)を指定して文書を開く**ための共通の契約を定める。この契約を使う者は次の3つ。

- `hyperbuf` CLI(`cli/`)
- Emacs 連携(`emacs/`)。プロトコルを直接扱わず、`hyperbuf` CLI を呼ぶ薄いラッパーとする(CLAUDE.md の方針)
- その他の利用者(シェルのスクリプト、他のツール、ターミナルのハイパーリンクなど)

対象外(初版):

- 文書内容の編集。HyperBuf はビューアで、編集は Emacs などに任せる。
- 検索、レイアウトの操作などの遠隔操作。初版は「開く」と、位置の問い合わせ(§11)にとどめる。
- アプリから外部エディタを起動する逆方向の連携(§9 の未決事項)。

## 2. 利用シーン

| 利用者                   | 例                                                                                                    |
| ------------------------ | ----------------------------------------------------------------------------------------------------- |
| ターミナル               | `hyperbuf docs/design.md`、`hyperbuf docs/design.md:120`、`hyperbuf docs/design.md --anchor 設計方針` |
| Emacs                    | 編集中の Markdown を、現在行つきでビューアに表示する(`M-x hyperbuf-open-file`)                        |
| コーディングエージェント | 生成・更新した設計文書を、ユーザーのビューアで開く                                                    |
| ターミナルのリンク       | エラー出力のファイル名・行番号から、クリックで開く                                                    |

## 3. 基本方針(提案)

1. **「開く」の正規の表現は URL とする。** `hyperbuf://open?...`。CLI はこの URL を組み立てて macOS に渡す薄いラッパーであり、他のツールも URL を直接使える。
2. **起動と受け渡しは macOS(Launch Services)に任せる。** アプリが未起動なら起動され、起動中なら実行中のインスタンスに URL が届く(単一インスタンス)。自前のソケットやデーモンは、初版では作らない。
3. **契約は小さく保つ。** 初版は `open` の1操作。未知のパラメータは無視し、未知の操作は拒否する。バージョン(`v`)を持つ。
4. **ファイルの内容は、アプリが読む。** CLI やアプリへのリンクは、パスと位置だけを運ぶ。
5. **安全側に倒す。** URL は Web ページや文書の中からも起動され得るため、受け取る側(アプリ)が範囲の検証を行う(§6)。

## 4. 契約

### 4.1 URL

```
hyperbuf://open?v=1&path=<絶対パス>[&line=<N>][&anchor=<ID>][&project=<絶対パス>][&target=<current|split-right|split-below|new-frame>]
```

| パラメータ | 必須     | 意味                                                                      |
| ---------- | -------- | ------------------------------------------------------------------------- |
| `v`        | いいえ   | 契約のバージョン。省略時は 1                                              |
| `path`     | **はい** | 開く Markdown の絶対パス。パーセントエンコードする。拡張子は `.md` のみ   |
| `line`     | いいえ   | 元の Markdown の行番号(1 始まり)。行アンカー `line:N` として扱う          |
| `anchor`   | いいえ   | 見出しなどのアンカー。`line` と同時に指定された場合は `anchor` を優先する |
| `project`  | いいえ   | プロジェクトのルート(絶対パス)。省略時は §5 の規則で決める                |
| `target`   | いいえ   | 表示先。省略時は `current`(選択中の window。履歴に積まれ、Back で戻れる)  |

- 位置の指定(`line` / `anchor`)は、既存のアンカー(`path#見出し`、`path#line:N`、`interaction-model.md` §5b)と同じ意味。
- 相対パスは拒否する(CLI が絶対パスに変換する)。
- パーセントエンコードされた制御文字、`..` を含むパス、`.md` 以外は拒否する。

### 4.2 CLI

```
hyperbuf [オプション] <ファイル>[:<行>]
```

| 項目                   | 内容                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------- |
| 位置指定               | `file.md:120`(行番号)。`--line N`、`--anchor ID` でも指定できる                                         |
| 複数のファイル         | 順に開き、最後のファイルを表示する(それ以前は buffer として残る)                                        |
| `--project DIR`        | プロジェクトのルートを明示する                                                                          |
| `--target <…>`         | `current`(既定)、`split-right`、`split-below`、`new-frame`                                              |
| `--no-activate`        | アプリを前面に出さない                                                                                  |
| `--print-url`          | 開かずに、組み立てた URL を出力する(確認・他ツールとの連携用)                                           |
| `--version` / `--help` |                                                                                                         |
| 動作                   | 引数を検証して絶対パスに直し、URL を組み立てて `open` に渡す。結果はアプリ内の表示に任せる              |
| 終了コード             | 0: 要求を渡した / 1: 使い方の誤り / 2: ファイルがない・読めない・`.md` でない / 3: アプリを起動できない |

**制約(提案の方式の限界):** `open` は要求を渡して即座に戻るため、CLI はアプリ内の結果(範囲外で確認待ちになった、など)を知らない。結果の通知が必要になった場合は、ソケット等の双方向の経路を追加する(§9)。

### 4.3 Emacs

`emacs/hyperbuf.el`(CLI の薄いラッパー)。

| コマンド                     | 動作                                                                                                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hyperbuf-open-file`         | 現在のバッファのファイルを、現在行つきで開く                                                                                                       |
| `hyperbuf-open-project-file` | 現在のプロジェクトの Markdown を選んで開く(旧称: `hyperbuf-open-project`。`open` 要求はファイルを指すため、プロジェクトのルートそのものは開けない) |
| `hyperbuf-open-other-window` | `--target split-right` で開く                                                                                                                      |
| `hyperbuf-open`              | Lisp から使う(`FILE &optional LINE ANCHOR TARGET WAIT`)                                                                                            |

- カスタマイズ変数: `hyperbuf-executable`(既定 `hyperbuf`)、`hyperbuf-default-target`。
- Emacs 側で見出しのアンカーは計算しない。行番号を渡し、アプリが該当ブロックへ解決する(GitHub 方式の見出し ID の計算を Emacs に持ち込まないため)。
- 将来: 編集位置の追従(カーソル移動にビューアが追従する)は、初版の範囲外。

## 5. アプリ側の挙動(提案)

1. **単一インスタンス。** URL は実行中のアプリに届く。未起動なら起動後に届く。
2. **ファイルの属するプロジェクトの決め方。** 次の順。
   1. `project` が指定されていれば、それ。
   2. すでに開いているプロジェクトのうち、そのファイルを含むもの。
   3. ファイルの最寄りの祖先で、`.git` を含むディレクトリ。
   4. ファイルのあるディレクトリ。
3. **表示先。** 既定は、前面の frame の選択中の window。参照履歴に積まれる(Back で元に戻れる)。`target` の指定があればそれに従う。
4. **複数のプロジェクト。** プロジェクトは frame に属する(`interaction-model.md` §8 の「複数 frame と Project の対応」は未決)。
5. **位置の解決。** `anchor` / `line` は、描画後の DOM から該当要素を探す(見出し・行アンカー)。見つからなければ、文書の先頭を開き、ミニバッファに通知する。
6. **エラーの通知。** 失敗(ファイルがない、`.md` でない、範囲外で拒否されたなど)は、ミニバッファに表示する。ダイアログは出さない。

## 6. セキュリティ(提案)

URL スキームは、Web ページ・メール・文書のリンクからも起動され得る。「CLI から来た要求」と「Web から来た要求」は、そのままでは区別できない。

- **操作は副作用のない「開く」だけ。** ファイルの変更・削除・外部コマンドの実行は、この契約に含めない。
- **読み取りの範囲を制限する。** アプリが信頼するプロジェクトのルートの内側のファイルだけを、確認なしで開く。それ以外(範囲外)は、**ミニバッファで確認する**(例: `/path/to/x.md は開いているプロジェクトの外です。開きますか? (y/n)`)。承認したルートは、永続化した「信頼するルート」の一覧に加える。
- **内容の扱いは通常と同じ。** 開いた文書は、`poc-rendering-results.md` §6 のとおり、不信任な入力として描画する。
- **パスの検証。** 絶対パス、`.md` のみ、`..` を含むパスの拒否、シンボリックリンクの解決後の再検証(ルート外への脱出の防止)、制御文字の拒否。
- **入力の検証。** `line` は正の整数のみ。`anchor` は長さを制限し、DOM の検索に使う際は必ずエスケープする(`CSS.escape`)。
- **代替案(未決):** CLI が、アプリのデータディレクトリにあるトークン(`0600`)を URL に付ける方式。トークンのない URL(Web 由来の可能性がある)は常に確認を要求し、あるものは範囲内を確認なしで開く。強い区別が可能になる一方、トークンの生成・更新・共有(Emacs や他ツールが CLI を経由する限り問題は小さい)の設計が増える。

## 7. 互換性

- `v` が未知のバージョンの場合は、要求を拒否してミニバッファに通知する。
- 追加のパラメータは、既存のものの意味を変えずに足す。未知のパラメータは無視する。
- 将来、双方向の経路(ソケット)を足しても、URL の契約は残す(CLI がフォールバックに使える)。

### 実装中に分かったこと

- SwiftUI の `WindowGroup` と `onOpenURL` の組み合わせは、URL ごとに新しいウィンドウを作ることが知られているため、`AppDelegate` で受ける構成にした(この点は、`WindowGroup` の側を実際には試していない)。

## 10. 逆方向の連携(ビューアから編集位置へ)

状態: **検討中** — 要件と方式の比較まで。方式は未決。

### 10.1 要件: 誤った場所を編集させない

背景(ユーザーの経験): 巨大な文書の記載ミスをビューアで見つけ、Emacs のインクリメンタルサーチで「該当箇所と思った場所」を修正したところ、**別の場所を修正してしまった。** 同じ文言が複数あり、見ていた位置と、検索で着いた位置が食い違っていた。

したがって、この連携は「近くまで連れていく」だけでは不十分で、次を満たす必要がある。

| #   | 要件                               | 意味                                                                                                                                     |
| --- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | **正確な位置を指す。**             | 文言の検索に頼らず、ビューアが元の Markdown 上の位置(行・桁、または範囲)を、構文木の位置情報から特定して渡す                             |
| R2  | **食い違いを黙って通さない。**     | 位置とあわせて「その位置にあるはずの文字列」を渡し、エディタ側で照合する。一致しなければ警告し、勝手に飛ばない                           |
| R3  | **古い表示を検出する。**           | ビューアが描画した時点のファイルの識別情報(内容のハッシュ、更新日時とサイズ)を渡す。エディタ側のファイルが変わっていれば、警告する       |
| R4  | **着いた場所を、目で確認できる。** | エディタ側で、対象の範囲を一時的に強調し、「ビューアが指していた文字列」をメッセージに表示する                                           |
| R5  | **曖昧さを隠さない。**             | 位置を一意に決められないとき(選択がなく、ブロック内に同じ文字列が複数あるなど)は、確実な範囲(ブロック全体)だけを渡し、「曖昧」と明示する |

### 10.2 位置の特定

- **ブロック単位は正確に取れる。** 描画時にブロック要素へ `data-source-line`(開始行)を付けており、構文木は終了位置も持つ。
- **ブロック内の細かい位置は、描画から元の位置への対応が失われる。** 強調、リンク、エスケープ、HTML エンティティで、見えている文字列と元の文字列が一致しない。
- **対応案:** ユーザーが選択した範囲(または指した位置)から、構文木の最小のノードを求め、その元の範囲を取る。インライン要素への位置情報の付与が必要。最小のノードが決まらないときは R5 に従う。
- **「どこを指しているか」を、利用者がどう示すか。** カーソルを表示しない方針のため、現状は手段がない。選択(マウス、キーボードのマーク)か、ブロック単位の目印が必要で、**未決の「コピーのためのテキスト選択」の設計と同じ問題**になる。

### 10.3 方式の比較

| 方式                                             | 内容                                                                                                         | 利点                                                                                                                              | 欠点                                                                                                                                                                |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. アプリがエディタを起動する(送り出し)          | ビューアのコマンドから、ユーザーが設定したコマンド(例: `emacsclient`)を実行する                              | ビューアの操作だけで完結する。多くのエディタに使える                                                                              | **外部コマンドの実行**(README のセキュリティ方針)。コマンド行や Lisp の式に値を埋め込むと、注入の危険。エディタ側での照合(R2・R3)には、結局エディタ側のコードが要る |
| B. エディタが取りに来る(引き取り)                | アプリが「現在の位置」を状態ファイル(アプリのデータディレクトリ、`0600`)に書き、Emacs のコマンドが読んで飛ぶ | アプリは外部コマンドを実行しない。**照合・強調・警告を、Emacs 側で完全に制御できる**(R2〜R4)。Emacs の利用者の操作(キー1つ)に合う | 利用者が Emacs 側で操作する必要がある。状態は更新時刻つきで、古いと分かるようにする(R3)                                                                             |
| C. エディタ固有の URL スキーム(`vscode://` など) | アプリが、エディタが登録した URL を開く                                                                      | 実装が簡単                                                                                                                        | 照合ができず、R2 を満たせない。エディタごとに異なる。Emacs には標準がない                                                                                           |

### 10.4 合意事項(2026-10-08)

1. **データの経路は B(エディタが取りに来る)を先に作る。** 外部コマンドの実行が要らず、R1〜R5 の照合を Emacs 側に置ける。Emacs のビルド(takaxp 版など)に依存せず、ファイルを読めれば動く。
2. **「指している場所」は、マウスで選択し、右クリックメニューで示す。** カーソルは表示しない方針のまま、編集は頻度が高くないため、この手段で十分とした。メニューには、macOS 標準の項目(翻訳など)と同じ場所に **「Emacs で編集」** を足す(§10.6)。
3. **R5: 曖昧なときは、ブロック全体への移動と警告にとどめ、推測で飛ばさない。**
4. **R3: ファイルが変わっていたときは、警告のみにする。続行する手段は設けない。** 何かが根本的におかしいことに、本人が気づいていないことが多いため、冷静に状況を判断する機会を与える(§10.7)。

### 10.5 位置の記述(ペイロード)の案

```json
{
  "v": 1,
  "path": "/abs/path/to/doc.md",
  "range": {
    "start": { "line": 120, "column": 5 },
    "end": { "line": 120, "column": 18 }
  },
  "precision": "exact | block",
  "expect": "ビューアが指している文字列(元の Markdown のまま)",
  "context": { "before": "直前の数十文字", "after": "直後の数十文字" },
  "file": { "sha256": "…", "mtime": "…", "size": 0 },
  "viewer": { "renderedAt": "…", "selection": "…" }
}
```

- `precision: block` は、位置が曖昧でブロック全体しか確実でないこと(R5)を示す。
- 照合は、`expect` が `range` の位置にあることと、`file` の識別情報が一致することの両方で行う。
- 置き場所: アプリのデータディレクトリ内の状態ファイル(`0600`)。更新のたびに原子的に置き換える。内容に文書の一部(`expect`、`context`)を含むため、他のユーザーから読めないようにする。

### 10.6 「Emacs で編集」メニューと位置の特定

**メニュー(macOS のネイティブ)**

- WKWebView を継承し、`willOpenMenu(_:with:)` で右クリックメニューに項目を足す(「翻訳」などの標準項目の並びに加える)。
- 項目の実行で、Web コアに現在の選択から位置を求めさせ、状態ファイルに書く。
- **起動のコマンド(任意):** 設定されていれば、固定のコマンドを実行して Emacs に取りに来させる(例: `emacsclient -n -e '(hyperbuf-edit-here)'`)。コマンドの文字列は**ユーザーが設定した固定のもの**で、文書の内容は一切含めない(注入の余地がない)。位置は状態ファイルで渡す。未設定なら、項目は「位置を記録」になり、Emacs 側のコマンド(`hyperbuf-visit-location`)で取りに行く。
- 外部コマンドの実行を伴うので、設定の保存場所と、実行を許可する手順(初回の確認など)を設計に含める。

**選択 → 元の位置(Web コア側)**

1. 選択の開始点を含む、最も内側のブロック要素を求める(`data-source-line` を持つ要素。終了位置と文字オフセットも持たせる拡張が必要)。
2. そのブロックの元の Markdown の範囲を取り出す。
3. 選択した文字列を、元の範囲の中で探す。**一意に見つかれば `exact`**(行・桁を計算する)。
4. 見つからない(強調・リンク・エスケープで元の文字列と一致しない)、または複数見つかる場合は、**`block`**(ブロック全体の範囲)にして、曖昧であることを示す。
5. 選択がない場合は、右クリックした位置のブロックを `block` として扱う。

### 10.7 Emacs 側の振る舞い(R2〜R4)

`hyperbuf-visit-location`(`emacs/hyperbuf.el`):

1. 状態ファイルを読み、更新時刻が古すぎないかを確認する。
2. **ファイルの識別情報(ハッシュ等)が現在のファイルと一致しなければ、移動しない。** 警告として「ビューアが描画した版と、現在のファイルが違う」ことを表示し、照合の詳細(期待した文字列と、実際の内容)を専用のバッファに表示する。続行する手段は設けない。
3. `expect` が `range` の位置にあるかを照合する。一致しなければ、同様に移動せず警告する。
4. 一致すれば、ファイルを開いて該当位置に移動し、範囲を一時的に強調し、ミニバッファに `expect` の文字列を表示する(R4)。
5. `precision: block` のときは、ブロックの先頭へ移動し、範囲全体を強調して、「位置が曖昧なため、ブロック全体を示しています」と表示する(R5)。

### 10.8 未決事項

2. **選択 → 元の位置のマッピングの精度。** インライン要素への位置情報の付与(強調・リンクをまたぐ選択を `exact` にできるか)は、実際の文書で検証が必要。
3. **起動のコマンド(任意)の設定と、実行の許可の手順。**
4. **ペイロードの共有範囲。** Emacs 以外のエディタのために、状態ファイルの形式を公開契約にするか。
5. **複数のウィンドウ・frame があるとき、どの位置を状態ファイルに書くか。** 直近に「Emacs で編集」を実行した位置、でよいか。

## 11. IPC(Unix ドメインソケット)

状態: **提案(方針は合意済み、サーバーの実機確認済み)** — 配布方式(§12)を受けて、CLI・Emacs 連携の主経路とする。結果は §11.7。

### 11.1 位置づけ

| 経路                | 用途                                                                             |
| ------------------- | -------------------------------------------------------------------------------- |
| **ソケット(IPC)**   | CLI・Emacs 連携の主経路。結果の応答、問い合わせ、確認の待ち合わせができる        |
| URL スキーム        | アプリの起動(未起動のとき)、外部リンクやターミナルのハイパーリンクからの「開く」 |
| 状態ファイル(§10.5) | ソケットが使えない場合の代替。第一候補ではなくなる                               |

- ソケットは、**アプリが起動している間だけ存在する。** CLI は、接続できなければ URL スキームでアプリを起動し、ソケットが現れるまで待ってから再接続する。
- ブラウザは Unix ドメインソケットに接続できないため、**Web 由来の要求はこの経路には来ない。** URL スキームより、要求の出所が絞られる。

### 11.2 トランスポート

| 項目             | 内容                                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 種類             | Unix ドメインソケット(ストリーム)                                                                                                                    |
| パス             | `~/Library/Application Support/HyperBuf/hyperbuf.sock`。`sun_path` は 104 バイトまでなので、長すぎる場合の代替パス(`$TMPDIR` 配下など)を定める(未決) |
| 権限             | ディレクトリ `0700`、ソケット `0600`                                                                                                                 |
| 接続元の確認     | 接続ごとに、相手のユーザー ID(`LOCAL_PEERCRED` / `getpeereid`)が、アプリと同じかを確認する。異なれば切断する                                         |
| 単一インスタンス | 起動時に既存のソケットに接続を試み、応答があれば、すでに起動中とみなす。応答がなければ古いソケットとして削除して作り直す                             |

### 11.3 メッセージ

UTF-8 の JSON Lines(1 行 1 メッセージ)。1 つの接続で、要求と応答を順に交換する。1 行の上限は 1 MiB。

要求:

```json
{
  "v": 1,
  "id": "1",
  "op": "open",
  "path": "/abs/doc.md",
  "line": 120,
  "target": "current"
}
```

応答:

```json
{"v":1,"id":"1","ok":true,"result":{"path":"rel/doc.md","project":"/abs/project"}}
{"v":1,"id":"1","ok":false,"error":{"code":"outside-project","message":"プロジェクトの範囲外です"}}
```

| 操作           | 内容                                                                                                                            | 応答の `result`                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `ping`         | 疎通とバージョンの確認                                                                                                          | `{ "version", "pid", "protocol": 1 }`                                                  |
| `open`         | §4.1 と同じパラメータで開く。範囲外の確認(ミニバッファ)が必要なときは、ユーザーの回答まで応答を保留する(既定 30 秒で `timeout`) | 開いた文書の相対パスとプロジェクト                                                     |
| `get-location` | 利用者が「エディタで編集」で指した位置(§10.5、`protocol/schema/location.schema.json`)を返す。まだなければ `null`                | `{ "location": ペイロード または null }`                                               |
| `get-view`     | いまの表示(どの文書の、どのあたりか)を返す。プロジェクト内の文書には、絶対パス(`absolutePath`)を添える                          | `{ "view": { "path", "anchor", "scrollTop", "history", "absolutePath" } または null }` |

| エラーコード                         | 意味                                                        |
| ------------------------------------ | ----------------------------------------------------------- |
| `bad-request`                        | 形式の誤り、必須項目の欠落、検証の失敗(§6 の入力検証と同じ) |
| `unsupported-version` / `unknown-op` | 契約のバージョン・操作が未対応                              |
| `not-found` / `not-markdown`         | ファイルがない / `.md` ではない                             |
| `outside-project`                    | 範囲外で、ユーザーが拒否した                                |
| `timeout`                            | ユーザーの回答が時間内になかった                            |
| `stale`                              | 位置が、古い表示に基づく(§10.7)                             |

- 未知のフィールドは無視する。未知の操作は `unknown-op` で応答する。
- 応答は要求の `id` で対応づける。同じ接続で複数の要求を並行してもよい。

### 11.4 CLI の流れ

1. ソケットに接続する。接続できなければ、`hyperbuf://ping`(URL スキーム)でアプリを起動し、最大数秒、ソケットの出現を待って再接続する。
2. 要求を送り、応答を待つ。
3. 応答に従って終了コードを返す。0: 成功 / 1: 使い方の誤り / 2: ファイルの問題 / 3: アプリを起動できない / 4: 拒否(範囲外・タイムアウトなど)。
4. `--wait` を付けない限り、アプリ内の確認待ちには長くは待たない(既定の短い期限)。

### 11.5 Emacs 側

**合意済み(2026-10-08):** Emacs の標準は**直接ソケット**とし、設定で CLI 経由にも切り替えられるようにする。

- 直接ソケット(標準): Emacs から `make-network-process`(`:family 'local`)で接続する。プロセス起動のコストがなく、`get-location` の往復が速い。JSON Lines の処理は、Emacs 側で数十行。
- CLI 経由(設定で切り替え): `hyperbuf` CLI を呼ぶ。プロトコルの知識が CLI の 1 か所に集まる。`hyperbuf-transport` を `cli` にする。
- **アプリが未起動のとき:** 直接ソケットでは接続できないため、既定では `open hyperbuf://ping`(URL スキーム)でアプリを起動し、ソケットの出現を待つ。起動したくない場合は、設定(`hyperbuf-launch-if-needed`)で無効にでき、その場合は「アプリが起動していません」と通知して終わる。

### 11.6 セキュリティ

- 接続できるのは、**同じユーザーのプロセスだけ**(権限と接続元の確認)。ブラウザやネットワーク越しには到達しない。
- 操作の集合は小さく固定し(`ping` / `open` / `get-location`)、副作用のある操作(ファイルの変更・削除、外部コマンドの実行)は含めない。
- `open` の入力検証は、URL 経由と同じ規則(絶対パス、`.md` のみ、`..` の拒否、シンボリックリンクの解決後の再検証、`line` と `anchor` の検証)。
- 範囲外のファイル: **URL 経由もソケット経由も、同じく確認する**(合意済み、2026-10-08)。ソケット経由は、確認の結果を CLI や Emacs が `--wait` 等で待てる。
- 状態の問い合わせ(`get-location`)の応答には文書の一部が含まれるため、接続元の確認を必須とする。
- 要求の大きさ・数の上限を設け、不正な形式の接続は閉じる。

### 11.7 実機確認(2026-10-08)

`poc/integration` ブランチ(`fc681bd`)に、Swift のサーバー(POSIX ソケット)と Python のクライアント試作を作って確認した。LaunchServices への登録は使っていない(アプリはパス指定で起動)。

| 項目                               | 結果                                                                                                                                                                                                                                                                            |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **権限**                           | ディレクトリ `drwx------`、ソケット `srw-------`(`bind` の時点から `umask` で 0600)                                                                                                                                                                                             |
| **コールドスタート**               | 未起動の状態から、CLI がアプリを起動し、ソケットの出現を待って、最初の `ping` が通るまで約 650 ms(2 回目は約 310 ms)。URL スキームで該当行を表示するまでの約 1.1 秒より速い                                                                                                     |
| **往復の遅延**                     | 同一接続での `ping` は、中央値 0.04 ms / p95 0.07 ms / 最大 0.24 ms。接続→`ping`→切断も中央値 0.03 ms。`open`(描画まで含めて応答)は約 146 ms                                                                                                                                    |
| **`open`(プロジェクト内、行指定)** | 該当行(`line:30`)が表示され、履歴に積まれ、応答が返る                                                                                                                                                                                                                           |
| **`get-location`**                 | 約 1 ms で、選択中の window の現在位置を返す(PoC では選択の代わりに現在位置)                                                                                                                                                                                                    |
| **異常系**                         | 不正な JSON、未知の操作(`delete`)、未対応の `v`、`path` なし、相対パス、`..` を含むパス、`.md` 以外、存在しないファイル、不正な `line`。いずれも対応するエラーコード(`bad-request`、`unknown-op`、`unsupported-version`、`not-markdown`、`not-found`)で応答し、アプリは落ちない |
| **範囲外ファイルの確認**           | 確認待ちの間、応答が保留され、期限(`timeoutMs`、既定 30 秒)を超えると `timeout` で応答する(1.2 秒の期限で、1,259 ms 後に応答)。ミニバッファでの回答も確認済み(yes: 成功、no: `outside-project`。§11.8)                                                                          |
| **大きすぎる行**                   | 2 MiB の 1 行は、接続を閉じる(エラー応答は届かない場合がある)                                                                                                                                                                                                                   |
| **パイプライン**                   | 同一接続に連続して送った複数の要求に、すべて応答する                                                                                                                                                                                                                            |
| **並行**                           | 100 接続を同時に張って、100 件とも成功(15 ms)                                                                                                                                                                                                                                   |
| **古いソケットの回復**             | `kill -9` でソケットファイルが残っても、次の起動で、接続を試して応答がないことを確認して作り直し、約 310 ms で `ping` が通る                                                                                                                                                    |
| **二重起動**                       | 2 つ目のプロセスは、既存のソケットに接続できることを検出する(`alreadyRunning`)。PoC では、検出後もウィンドウが残った。本実装では、検出したら既存のインスタンスを前面に出して終了する                                                                                            |

## 13. 実装の記録(M4、2026-10-09)

実装(`protocol/`、`app/macos/`、`cli/`)で確定した点。仕様の追記・変更。

- **CLI の起動の流れ:** ソケットに接続できなければ、**最初のファイルの `hyperbuf://open?…` で、アプリを起動する**(起動と、最初の要求の引き渡しが、1 回で済む)。起動の場合、CLI は結果を待たずに、終了コード 0 で終わる(結果は、アプリの画面に出る)。複数のファイルのときは、起動後、ソケットの出現を待って、残りを順に送る。
- **プロジェクトが決まっていないとき**(アプリの起動直後に、外部の要求が届いた場合): 要求を保留し、そのファイルの `.git` の祖先(なければ、ファイルのあるディレクトリ)を最初に表示する「プロジェクトを選ぶパネル」を出す。**利用者が選んだディレクトリだけが、読む範囲になる**(要求だけで、範囲は決まらない)。選ばれなければ、待っていた要求は `outside-project` で終わる。
- **範囲外の確認と、信頼するルート:**
  - Web コアのミニバッファに、「<ルート> を信頼して、<パス> を開きますか(プロジェクトの外です)?」と出る。
  - 承認されたら、Web コアが `host.confirmOutside(id, true)` を呼び、**アプリが提案したルートだけ**(要求の id に紐づく)が、信頼するルートに加わる。Web 側から、任意のルートは足せない。
  - 信頼するルートは `~/Library/Application Support/HyperBuf/trusted-roots.json`(ディレクトリ 0700、ファイル 0600、一時ファイルに書いてから置き換える)に保存する。
  - 文書の内側の画像は、プロジェクト内は `hyperbuf://project/…`、信頼するルートの内側は `hyperbuf://trusted/…` で配る。
- **期限切れ:** 要求の `timeoutMs`(既定 30 秒、CLI は 3 秒、`--wait` は 60 秒)を過ぎると、`timeout` で応答し、**画面に残っている確認も取り消す**(`onOpenCancel`)。
- **応答のないクライアント:** サーバーは、クライアントが送信側を閉じても(半クローズ)、未応答の要求があるあいだは、接続を閉じない。同一の接続の複数の要求は、並行して処理され、応答は 1 回だけ書かれる。
- **ソケットの権限:** `umask` は使わない(プロセス全体の設定で、他のスレッドのファイル作成に影響する)。置き場所のディレクトリを先に 0700 にし、`bind` のあとに `chmod 0600` する。接続ごとに、相手のユーザー ID を確認する。
- **`anchor` の長さ:** JSON Schema の `maxLength` と同じく、Unicode のコードポイントで数える(書記素ではない)。
- **共有する例:** `protocol/examples/` の `open-validation.json`、`url.json`、`framing.json`、`cli-args.json` を、Swift(プロトコル・CLI)と JSON Schema の検査が共有する。Emacs 連携(M5)も、同じ例を使う。
- **未実装・未確認:** `target`(分割・新規 frame)と `project` の処理(`project` は、アプリの起動時のパネルの初期位置だけに使う)、別のユーザーからの接続の拒否(`getpeereid`)の実機確認、署名・公証したアプリでの動作、二重起動の検出後に、既存のインスタンスを前面に出す動作(今は終了するだけ)、Emacs 側のクライアント。

## 14. Emacs 連携の実装の記録(M5、2026-10-09)

`emacs/hyperbuf.el`(Emacs 29.1 以上)。使い方・設定は `emacs/README.md`。

- **標準は直接ソケット**(`make-network-process` の `:family 'local`)。`hyperbuf-transport` を `cli` にすると、`hyperbuf` コマンドを呼ぶ。JSON は Emacs 組み込みの `json-serialize` / `json-parse-string`(ライブラリの追加なし)。
- **入力の検証を、Emacs 側にも持つ**(`hyperbuf--validate-open`)。接続の前に、利用者に、すぐ分かる形でエラーを返し、アプリが起動していない場合(サーバーが検証できない)にも、同じ規則で守る。規則がサーバーとずれないよう、`protocol/examples/open-validation.json` を共有して適合テストをする(例を壊すと、Emacs のテストも失敗することを確認した)。
- **URL の組み立ても共有の例で検証する**(`protocol/examples/url.json` の `url` と、Emacs が作る URL が一致する)。`url-hexify-string` は、予約文字と日本語を、大文字の 16 進でパーセントエンコードするので、Swift 側の `URLComponents` が読める。
- **アプリが起動していないとき:** `hyperbuf-launch-if-needed`(既定 t)なら、開く要求の URL で `open` する。結果は、アプリの画面に出る(CLI と同じ)。nil なら、通知して終わる。
- **未保存のバッファ:** ビューアはディスクを読むので、`hyperbuf-save-before-open`(既定 `ask`)で、開く前に保存を尋ねる。
- **TRAMP のファイルは開かない**(手元のファイルだけを、ビューアが読む)。
- **待ち時間:** アプリが `timeoutMs` で `timeout` を返すのを待つため、クライアントは、それに 2 秒の余白(`hyperbuf--reply-slack`)を足して待つ。
- **未実装:** `hyperbuf-visit-location`(ビューアから Emacs への編集位置の連携、M6)。

## 15. 逆方向の連携(編集位置)の実装の記録(M6、2026-10-09)

§10 の要件 R1〜R5 の実装。配置: `core/src/locate.ts`(元の位置への対応づけ)、`app/macos/Sources/HyperBufKit`(`FileFingerprint`・`LocationBuilder`・`EditorCommand`)、`emacs/hyperbuf.el`(`hyperbuf-visit-location`)、`protocol/schema/location.schema.json`・`protocol/examples/location*.json`。

### 流れ

1. 利用者が、ビューアで、文字列を選択して(または、右クリック、または何も選ばず)、右クリックメニューの **「Emacs で編集」**(または、キー `C-c e` / `M-x edit-in-editor`)を選ぶ。メニューの名前は、設定の `editorName`(既定 Emacs)。コマンドが設定されていなければ、「エディタ用に位置を記録」。
2. Web コアが、**指した場所を、元の Markdown の位置にする**(下記)。
3. アプリが、絶対パスと、**ビューアが描画した版のファイルの識別情報**(SHA-256・更新日時・サイズ)を足して、記録する。設定された固定のコマンドがあれば、実行する。
4. エディタが、`get-location` で取りに来て、**照合してから**、移動する。

### 指した場所 → 元の位置(R1・R5)

- 描画のとき、ブロック要素(段落・見出し・リスト項目・コード・表・引用など)に、元の Markdown の開始・終了のオフセットと行を残す(`data-source-start`・`data-source-end`・`data-source-line`・`data-source-end-line`)。
- 選択した文字列が、**そのブロックの元の文章の中で、ちょうど 1 か所**に見つかるときだけ、**`exact`**(その範囲)にする。
- 見つからない(強調・リンク・エスケープで、見えている文字列が、元と違う)、複数ある、選択がない(右クリックだけ・画面の上端のブロック)、複数のブロックにまたがる、のいずれかなら、**`block`**(ブロック全体、またがるときは、その全体)にして、曖昧であることを、画面にも出す。**推測で、位置を決めない。**
- 桁は、**Unicode のコードポイント**で数える(Emacs の文字の数と同じ。絵文字などの UTF-16 の違いに影響されない)。改行は、CRLF・CR・LF のどれでも、行を数える。`expect` と文脈は、改行を LF にそろえる。
- `expect` は、先頭 500 コードポイントまで(`expectTruncated`)。前後の文脈は、40 文字ほど(行をまたいでよい)。

### 照合と警告(R2・R3・R4)

エディタは、移動の前に、次を、この順に照合する。**失敗したら、移動も、続行もしない**(根本的に何かがおかしいことに、本人が気づいていないことが多いので、冷静に状況を判断する機会を与える)。

1. **`stale`:** ディスク上のファイルの SHA-256 が、`file.sha256`(ビューアが描画した版)と違う。
2. **`mismatch`:** 位置が、文書の範囲外 / その位置の文字列が `expect` と違う(切り詰められているときは、先頭だけ) / 前後の文脈が違う。**未保存の編集で、位置がずれているときも、ここで検出する**(バッファの内容を、照合する)。
3. 失敗のとき: 警告(`user-error`)と、食い違いの詳細(`*hyperbuf-mismatch*`: ビューアが指していた文字列、いまの文字列、SHA-256 の違い、対処)を出す。
4. 成功のとき: 範囲を一時的に強調し、ビューアが指していた文字列を表示する。`block` のときは、「位置が曖昧なため、ブロック全体を示しています」と出す。指した位置が 10 分(`hyperbuf-location-max-age`)より古いときは、その旨を添える。

照合の規則は、`protocol/examples/location-check.json` で共有し、Emacs の適合テストで検証する。

### エディタの呼び出し(外部コマンドの実行の権限設計)

設定ファイル `~/Library/Application Support/HyperBuf/config.json`(利用者が書く):

```json
{
  "editorName": "Emacs",
  "editorCommand": [
    "/opt/homebrew/bin/emacsclient",
    "-n",
    "-e",
    "(hyperbuf-edit-here)"
  ]
}
```

- コマンドは、**利用者が書いた固定のもの**だけ。**文書の内容・選択・パス・位置は、引数にも環境にも一切含めない**(位置は、エディタが `get-location` で取りに来る)。注入の余地がない。
- **シェルを介さず**、引数の配列で実行する。先頭は、実在する**実行可能な絶対パス**(`PATH` の検索を許さない)。引数は 16 個まで、各 1024 文字まで、NUL を含まない。満たさなければ、設定を無視する(エディタを呼び出さない)。
- 標準入出力は使わない。期限(5 秒)を過ぎたら、終了させる。
- 設定がなければ、エディタは呼び出さず、位置を記録するだけ(エディタ側で `M-x hyperbuf-visit-location`)。

### 実装で確定したこと

- 古い `get-location`(いまの表示を返していた PoC の挙動)は、**`get-view`** に分けた。`get-location` は、利用者が指した位置だけを返す。
- **仮想 buffer(検索結果など)は、編集の対象にならない**(エディタで開けるファイルがない)。指した位置は、変わらない。
- ビューアが読んでいないファイル、プロジェクトの外で信頼するルートの外のファイルの位置は、エディタに渡さない。
- **ファイルの識別情報は、ビューアに渡したバイト列**から求める(文字列にする前なので、不正な UTF-8 を含むファイルも、ディスクと一致する)。ファイルが変わって、ビューアが読み直したあとも、すでに指した位置の識別情報は、古いまま(= 古い表示に基づく位置だと、エディタが分かる)。
- **UTF-8 以外の文字コードのファイル**(Shift-JIS など)は、ビューアが UTF-8 として読むため、`expect` が合わず、`mismatch` になる(警告で止まる。誤った場所へは、移動しない)。

### 未検証・未実装

- ~~ネイティブの右クリックメニューの項目の、実機での操作~~ — **確認済み(2026-10-09、手動)**。位置の記録のみ(設定なし)と、`emacsclient` の呼び出し(設定あり)の両方で、期待どおりに動いた(メニューの項目が一番上に出る、選ぶと位置が記録される、Emacs が前面に出て移動する、曖昧な選択は block、未保存の編集・ファイル変更・検索結果は、移動せず警告、不正な設定は無視される)。
- 位置の指定の、キーボードだけの操作(選択のためのマーク)。`C-c e` は、選択がなければ、画面の上端のブロックを指す。
- 強調・リンクをまたぐ選択を、`exact` にすること(今は `block`)。実際の文書での、`block` になる頻度の確認。
- 署名・公証したアプリから、外部コマンドを実行できること(Hardened Runtime でも、子プロセスの実行は、制限されない想定だが、未確認)。

## 16. プロジェクトを持たない設計への変更(M7b、2026-10-10)

[project-model.md](project-model.md) に従い、アプリは「プロジェクト」を持たない。連携の契約への影響は次のとおり。§5(アプリ側の挙動)・§6(セキュリティ)・§9・§13 の、プロジェクトに関する記述は、ここで置き換える。

### 16.1 要求

- `path` は、**絶対パス**(従来どおり)。`project` と `--project` は、**受け取るが、使わない**(後方互換のため。プロジェクトの単位がない)。
- 応答の `result.path` と `get-view` の `path` は、**絶対パス**(`realpath` の形)。`get-view` の `absolutePath` は、`path` と同じ値(互換のために残す)。
- ファイルを開く範囲は、**プロジェクトではなく、許可パスと警告パスで決まる**。判定の規則と設定(`warnPaths` / `allowPaths`)は、project-model.md §5 と [configuration.md](configuration.md)。

### 16.2 経路による判定の違い

| 経路                                           | 判定                                                                                                                                                                                                                     |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ソケット(CLI、Emacs。**CLI の初回起動を含む**) | パスの規則だけで判定する。警告パスのファイルは、ミニバッファで確認する(承認すると、そのファイルのディレクトリ以下を記憶する。ただし、警告パスそのもの、またはその上位のディレクトリは、記憶せず、ファイル単体を記憶する) |
| **URL スキーム**(`hyperbuf://open?…`)          | 起点を特定できない(Web ページなどからも起動できる)ので、**許可パス(設定の `allowPaths` と、記憶したパス)にないファイルは、警告パスの外でも確認する**                                                                     |

- 確認の拒否・期限切れは、これまでどおり `outside-project` / `timeout`(`outside-project` は、「警告パスのため開かれなかった」の意味になる)。
- 確認は、**行き先のフレームのミニバッファ**に出る。行き先は、最後にアクティブだったフレーム(project-model.md §10)。

### 16.3 CLI

- **初回起動:** アプリが起動していないとき、`hyperbuf://ping`(起動だけ)でアプリを起動し、ソケットが現れるまで待ってから、**ソケットで「開く」を送る**(従来は、最初のファイルの `hyperbuf://open?…` で起動していた)。URL スキームの確認を避け、CLI と Emacs の要求を、すべてソケットに通すため。複数のファイルは、順に送る。
- **ディレクトリを渡す:** `hyperbuf DIR` は、`DIR/index.md`、なければ `DIR/README.md` を開く(どちらもなければ、失敗する)。
- `--project` は、無視する。

### 16.4 アプリ

- 起動の引数・Finder の「このアプリケーションで開く」も、同じ規則(ファイル、またはディレクトリの `index.md` / `README.md`)。
- 記憶したパスは、従来の `trusted-roots.json` をそのまま使う(形式は変わらない。ディレクトリに加えて、ファイル単体も入る)。
- `get-location` / `get-view` は、**最後にアクティブだったフレーム**(`get-location` は、位置を記録したフレーム)のものを返す。
- 画像などのリソースは、`hyperbuf://file/<絶対パス>` で配り、**読み込みのたびに判定する**(警告パスの画像は、読み込まれない)。

# プロジェクトとファイルの扱い(初期案)

状態: **初期案(未実装)**。決定した項目と、議論中の項目を、項目ごとに記す。M7 の次、M8(配布)の前に、1 つのマイルストーンとして実装する案。

凡例: **【決定】** 合意済み / **【議論中】** 提案があり、合意待ち / **【未決】** 案がまだない。

## 1. 方針【決定】

Emacs の流儀に合わせる。**バッファが主役で、基準は「現在のバッファのファイルのディレクトリ」**(Emacs の `default-directory`)。「プロジェクトを選ぶ」操作はない。

- バッファの識別は、**絶対パス**(`realpath` で正規化)。
- ファイルを開く・検索する範囲は、現在のバッファのディレクトリから決まる。
- 「プロジェクト」は、あれば便利な範囲指定(`project.el` と同じ位置づけ)で、必須ではない。
- アクセスの安全は、プロジェクトではなく、**許可パス / 警告パス**で決める(§5)。
- セッションは、全体で 1 つ。起動時は、前回の状態を復元する(なければ、空の画面)。

## 2. 基準のディレクトリ(`default-directory`)【決定】

| バッファ                       | 基準のディレクトリ                         |
| ------------------------------ | ------------------------------------------ |
| ファイルの文書                 | そのファイルのディレクトリ                 |
| 仮想バッファ(`*search: …*`)    | 検索の起点のディレクトリ                   |
| 仮想バッファ(`*Help: …*` など) | 直前に選択していたバッファのものを引き継ぐ |
| バッファがない(起動直後)       | ホスト(`~`)                                |

ミニバッファを開くときは、開いた時点で選択していたバッファの基準を使う。

## 3. ファイルを開く(`C-x C-f`)

- 入力欄は、基準のディレクトリ(`~/` 形式に短縮して表示)から始まる。【決定】
- 候補は、入力済みのディレクトリの中の **`.md` ファイルとサブディレクトリ**(隠しファイルは、入力が `.` で始まるときだけ)。【決定】
- `~/`、`../`、絶対パスの入力に対応する。`TAB` で補完する。【決定】
- **ディレクトリは、`RET` で確定しない**。ディレクトリを選んで `RET` を押すと、その中に入る(入力欄の末尾が `/` になり、候補が更新される)。【決定】
- **`.md` のファイルを指定したときだけ、開く**。`.md` 以外、存在しないファイルは、メッセージを出して開かない(ビューアなので、新規作成はしない)。【決定】
- 自分で打ったパスは、利用者の意思そのものなので、**警告の判定をしない**(§5)。【決定】
- 候補の絞り込みに、パスの断片へのあいまい一致(`ar/in` で `architecture/index.md` など)を使う。【議論中】
- ホストの契約: 入力欄の補完用に、1 階層だけを返す `listDirectory(dir)` を置く。再帰の一覧(`C-x p f`、検索)とは別にする。【議論中】

`C-x p f`(新規)は、現在のプロジェクトの全文書を一覧にして絞り込む。今の `C-x C-f` の動きは、これに移す。【決定】

### 3.1 ディレクトリを開く【決定】

`hyperbuf <ディレクトリ>`(CLI、Finder の「このアプリケーションで開く」、ドラッグ&ドロップ、`swift run HyperBuf <dir>` など)は、そのディレクトリの **`index.md`、なければ `README.md`** を開く。どちらもなければ、そのディレクトリで `C-x C-f` の入力欄を開く。

これまでの使い方(プロジェクトのディレクトリを渡して開く)と、統合テストの起動が、そのまま通る。

## 4. プロジェクトと検索

- **プロジェクト**(`C-x p f` の範囲): 基準のディレクトリから上へたどり、最初に目印がある場所。なければ、基準のディレクトリそのもの。【決定】
- 目印(`projectMarkers`)の既定: `.git`、`.hg`、`.hyperbuf`。`.hyperbuf` は、利用者が置く空のファイルかディレクトリで、目印のない場所を、明示的にプロジェクトにする。【議論中】
- **全文検索 `M-s g`**: **基準のディレクトリ以下だけ**を再帰で検索する(プロジェクトのルートまでは広げない)。検索結果の仮想バッファは、起点を基準にする。【決定】
- 検索の守り【決定】:
  - `~` と `/` は、検索の起点として**拒否**する(メッセージを出す)。
  - 件数(ファイル数)と時間に**上限**を設ける。超えたら、打ち切って、そう知らせる。
  - 検索は**キャンセルできる**(`C-g`)。
  - 外付けディスクやネットワークボリュームでは、列挙に**タイムアウト**を設ける。
- 一覧と検索の対象は、今までどおり `*.md` と、ディレクトリだけ。隠しファイルと `node_modules` は除く。【決定】

## 5. アクセスの判定(許可パスと警告パス)

### 5.1 判定の対象【決定】

次の経路は、すべて同じ判定を通る(判定は Swift 側の `FileAccess` が行い、Web コアは確認の表示だけを担当する)。

- リンクのクリック
- CLI・Emacs・URL スキームからの「開く」
- 文書が参照する画像などのリソース

`C-x C-f` で打ったパスは、判定しない。

### 5.2 経路による扱いの違い【決定】

URL スキーム(`hyperbuf://open?...`)は、ブラウザ上の任意のページなど、**起点を特定できない**経路から起動できる。パスの規則だけで判定せず、起点で扱いを分ける。

| 経路                                | 判定                                                                   |
| ----------------------------------- | ---------------------------------------------------------------------- |
| ソケット(CLI、Emacs)                | 同一ユーザーのプロセスなので、パスの規則(§5.3)だけで判定する           |
| **URL スキーム**                    | 許可パスにないファイルは、**警告パスの外でも、ミニバッファで確認する** |
| リンクのクリック、リソース          | パスの規則(§5.3)だけで判定する                                         |
| `C-x C-f`、ミニバッファで打ったパス | 判定しない(利用者の意思)                                               |

### 5.3 パスの規則【議論中】

パスを正規化(`realpath`。シンボリックリンクは実体で判定する)したうえで、設定に書かれた**許可パス**と**警告パス**を照合する。

1. どちらにも一致しなければ → **開く**。
2. 一致するものがあれば、**一番長く一致したもの**が勝つ(より具体的な指定が優先)。
   - 許可パスが勝つ → 開く。
   - 警告パスが勝つ → ミニバッファで確認する。
3. 許可と警告が**同じパス**で重なっていれば、安全側の警告にして、設定の問題として報告する。

| 設定                                               | ファイル               | 結果                   |
| -------------------------------------------------- | ---------------------- | ---------------------- |
| `trustedPaths: ~/work`、`warnPaths: ~/work/vendor` | `~/work/vendor/x.md`   | 警告(具体的な方が勝つ) |
| `trustedPaths: /usr/share/doc`、`warnPaths: /usr`  | `/usr/share/doc/a.md`  | 許可                   |
| (どちらにも一致しない)                             | `~/Downloads/foo/a.md` | 開く                   |

パスの一致は、区切りの境界で判定する(`/tmp` が `/tmp2` に一致しない)。存在しないパスの比較は、大文字小文字を区別しない(APFS)。

### 5.4 確認と記憶

- 警告パスのファイルを開くときは、ミニバッファで確認する(今の「範囲外のファイル」の確認と同じ操作)。【決定】
- 承認すると、そのファイルのディレクトリ以下を記憶し、次からは確認しない(記憶は永続化する。実質は具体的な許可パスとして働く)。【決定】
- **記憶の範囲の制限**【決定】: 記憶するディレクトリが、**警告パスそのもの、またはその上位**になる場合は、ディレクトリではなく、**そのファイル単体**だけを記憶する(`/tmp/x.md` を承認して、`/tmp` 全体が許可になるのを防ぐ)。
- まとめて許可したい場所は、`trustedPaths` に書く。【決定】
- 記憶したパスの**一覧と取り消し**のコマンド(`M-x forget-trusted-path` など)を設ける。記憶の保存先は、利用者が書く `config.json` とは別のまま(アプリは設定ファイルを書き換えない)。既存の `trusted-roots.json` は、記憶したパスとして引き継ぐ。【議論中】

### 5.5 画像などのリソース【議論中】

リソースは、文書の描画中に非同期で読み込まれるので、その場で確認を出して止められない。次の流れにする。

1. 描画の**前**に、文書内のローカル画像のパスを集めて、まとめてホストに判定させる。
2. 警告対象のリソースは、読み込まずに、プレースホルダーを出す。
3. 描画のあとに、「警告対象のパスの画像が N 件あります(`<ディレクトリ>`)。許可しますか?」とミニバッファで一度だけ聞く。
4. 承認したら、そのディレクトリを記憶し、描画し直す。断った場合は、**そのセッションの間は覚えて**、ファイルの更新による再描画で聞き直さない。
5. 許可・拒否の**最終判定は、スキームハンドラ側で必ず再確認する**(Web コアの判断を信用しない。今と同じ)。

### 5.6 既定値【議論中】

- `warnPaths` の既定: `/usr`、`/opt`、`/tmp`、`/var`、`/etc`、`/System`、`/Library`、および、ホスト配下の機微な場所 `~/.ssh`、`~/.aws`、`~/.gnupg`、`~/Library`。
- `trustedPaths` の既定: なし。`/Volumes`(外付けドライブ)は、警告に入れない(自分の文書を、毎回確認されないように。代わりに、列挙のタイムアウトで守る)。
- `trustedPaths` は、警告パスと重なる場所でだけ意味を持つ。名前を `allowPaths` にするかは、未決。

macOS では `/tmp`、`/var`、`/etc` が `/private/...` へのシンボリックリンクなので、設定のパスも、読み込み時に正規化して照合する。存在しないパスは、文字列のまま使う。

## 6. 設定(`config.json`)【議論中】

```json
{
  "warnPaths": ["/usr", "/opt", "/tmp", "/var", "/etc", "/System", "/Library"],
  "trustedPaths": ["~/work", "/usr/share/doc"],
  "projectMarkers": [".git", ".hg", ".hyperbuf"]
}
```

- `warnPaths` は、書いたら既定の一覧を**置き換える**。`[]` で警告なし。
- `~` は展開する。絶対パスでないもの、型が違うものは、無視して理由を `C-h b` の「設定の問題」に出す。

## 7. セッションと起動【決定】

- セッションは、全体で 1 つ(プロジェクトごとではない)。保存先は、`~/Library/Application Support/HyperBuf/session.json`(0600)。
- 起動時は、前回の状態を復元する。保存がない・壊れていれば、空の画面に「`C-x C-f` で開く」と出す。
- `hyperbuf <ファイル>` で開いたときは、復元した状態に、そのファイルを開く。
- 移行: M7 のプロジェクトごとのセッションは、破棄する(利用者は作者のみ)。

## 9. 段階案【議論中】

1. **段階 1:** バッファの絶対パス化、基準のディレクトリ、`C-x C-f` のパス補完、検索の起点と守り、全体セッション。
2. **段階 2:** 許可/警告パスの判定、設定、確認と記憶、リソースの流れ、URL スキームの扱い。
3. **段階 3:** `C-x p f`、バッファ名の区別、表示の整理。

**段階 1 と 2 は、1 つのブランチにまとめて、1 度にマージする**(バッファの識別とアクセス判定は、どちらも `FileAccess` にかかるので、段階 1 だけをマージすると、判定が中途半端になる)。ブランチの中では、段階ごとにコミットを分ける。

## 10. 決めていないこと

- 警告パスの既定の一覧の最終形(§5.6)。`trustedPaths` を `allowPaths` に改名するか。
- 目印(`projectMarkers`)の既定の最終形(§4)。
- ファイル監視の方式: 開いているバッファの親ディレクトリごとに FSEvents を張り、開いているパスだけに絞る案(`~` 直下のファイルは、イベントが多くなる点が懸念)。
- バッファの表示名(プロジェクトのルートからの相対か、`~/…` か、区別のための接頭辞の規則)。
- `C-x C-f` の補完の仕様(あいまい一致の範囲、`listDirectory` の件数の上限)。
- 複数のウィンドウを開く場合の扱い(現在はウィンドウ 1 つ。全体で 1 つのセッションとの組み合わせは、ウィンドウを増やすときに別途設計する)。

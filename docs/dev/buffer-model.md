# バッファ・モデル

HyperBuf の中心概念である**バッファ**の定義と、そこから導かれる仕組み(基準のディレクトリ、ファイルを開く操作、一覧と検索の範囲、プロジェクト・ルート、フレームとの関係、外部の変更への追従、永続化)をまとめる。

関連する文書:

- 操作モデル全体(window の分割、参照履歴、キー): [interaction-model.md](interaction-model.md)
- ファイルを開くときのアクセス判定(許可パス・警告パス): [file-access.md](file-access.md)
- 設定キーの一覧: [configuration.md](../user/configuration.md)
- セッションの復元: [session-restore.md](session-restore.md)

## 1. 概要

HyperBuf は Emacs の流儀に合わせ、**バッファを主役**にする。

- **バッファ**は、開いている文書そのもの。表示(window)や作業場(フレーム)とは別の存在で、同じバッファを複数の window に表示できる。
- バッファの識別は**絶対パス**。文書の置き場所によらず、`~/notes/a.md` も `/usr/share/doc/b.md` も、同じ扱いで開く。
- すべての操作の基準は、**現在のバッファのファイルのディレクトリ**(Emacs の `default-directory`)。ファイルを開く入力欄も、一覧も、検索も、ここから始まる。
- 「プロジェクトを選ぶ」操作は**ない**。プロジェクトは、バッファから計算する「ルートのディレクトリ」にすぎない(§6)。
- セッションは全体で 1 つ。起動時は前回の状態を復元する。

## 2. バッファ

### 2.1 識別と種類

| 種類                     | 識別                                          | 例                    |
| ------------------------ | --------------------------------------------- | --------------------- |
| ファイルのバッファ       | 絶対パス(`realpath` で正規化。実体で判定)     | `~/notes/a.md`        |
| 仮想バッファ(検索結果)   | `*search: …*`(検索の起点のディレクトリを持つ) | `*search: foo*<docs>` |
| 仮想バッファ(ヘルプなど) | `*Help: …*` など                              | `*Help: bindings*`    |

- ファイルのバッファの対象は `.md` だけ。ビューアなので、存在しないファイルを新規作成することはしない。
- アンカー(`#見出し`、`#line:N`)は、バッファの識別には含めない。参照履歴のエントリの位置である。

### 2.2 開く・閉じる

バッファは、次の操作で作られる(すでに開いていれば、そのバッファに移る)。

- `C-x C-f`、`C-x p f`(§5、§6)
- 文書内のリンク
- CLI・Emacs・URL スキームからの「開く」([integration-protocol.md](integration-protocol.md))
- セッションの復元(§9)

`C-x k` で閉じる。バッファの一覧はフレームごとに持つ(§7)。

## 3. バッファの名前と表示

識別は絶対パス(§2.1)だが、画面に出す**名前**は、Emacs の `uniquify` と同じ考え方で決める。

- **基本は、ファイル名(basename)**。例: `buffer-model.md`。
- 開いているバッファの中に**同じ名前が複数あるときだけ**、親ディレクトリを足して区別する。形式は Emacs の既定(`post-forward-angle-brackets`)に合わせ、`名前<区別の接尾辞>`。例: `README.md<docs>`、`README.md<emacs>`。接尾辞は、区別がつく最小の、ディレクトリの末尾側の部分(足りなければ `README.md<a/docs>` のように、上へ伸ばす)。
- 名前は**動的**: バッファが開く・閉じる(`C-x k`)と、衝突の有無が変わり、名前も変わる(Emacs と同じ)。識別は絶対パスなので、履歴・セッション・選択範囲には影響しない。
- プロジェクトという単位は持たないので、名前にも含めない。
- アンカーは、名前に付けない。
- **仮想バッファ**(`*search: …*`)は、検索の**起点の短いパス**を添える: `*search: foo*<docs>`(接尾辞の決め方は、ファイルと同じ。起点が `~` なら `<~>`)。検索結果の各ヒットは、起点からの相対パスで表示する。`*Help: …*` は、そのまま。

### 3.1 表示する場所

| 場所                     | 表示                                                      |
| ------------------------ | --------------------------------------------------------- |
| ウィンドウのモードライン | `buffer-model.md  Top  L1  [History 2/5]`                 |
| `C-x b` の候補           | バッファ名。最近使った順                                  |
| エコー、エラー           | バッファ名(ファイルを示すときは、`~/` で短縮した絶対パス) |
| 位置情報(エディタ連携)   | 絶対パス                                                  |

### 3.2 表示は最小限にする

UNIX / Emacs の、切り詰めた UI の美学を尊重し、表示を増やさない。

- モードラインの名前は、バッファ名だけ(ディレクトリも、アンカーも添えない)。`C-x b` の候補も、バッファ名だけ。
- 場所が分からなくなったときは、Emacs と同じく、`C-x C-f` を押して確かめる(入力欄は、基準のディレクトリから始まる)。確かめたら `C-g` で戻る。
- そのために、ツールチップや、絶対パスを表示するコマンド(`C-h f`)は、設けない。

## 4. 基準のディレクトリ(`default-directory`)

| バッファ                       | 基準のディレクトリ                         |
| ------------------------------ | ------------------------------------------ |
| ファイルのバッファ             | そのファイルのディレクトリ                 |
| 仮想バッファ(`*search: …*`)    | 検索の起点のディレクトリ                   |
| 仮想バッファ(`*Help: …*` など) | 直前に選択していたバッファのものを引き継ぐ |
| バッファがない(起動直後)       | ホスト(`~`)                                |

ミニバッファを開くときは、開いた時点で選択していたバッファの基準を使う。

## 5. バッファを開く(`C-x C-f`)

- 入力欄は、基準のディレクトリ(`~/` 形式に短縮して表示)から始まる。
- 候補は、入力済みのディレクトリの中の **`.md` ファイルとサブディレクトリ**(隠しファイルは、入力が `.` で始まるときだけ)。
- `~/`、`../`、絶対パスの入力に対応する。`TAB` で補完する。
- **ディレクトリは、`RET` で確定しない**。ディレクトリを選んで `RET` を押すと、その中に入る(入力欄の末尾が `/` になり、候補が更新される)。
- **`.md` のファイルを指定したときだけ、開く**。`.md` 以外、存在しないファイルは、メッセージを出して開かない。
- 自分で打ったパスは、利用者の意思そのものなので、**アクセスの判定をしない**([file-access.md](file-access.md))。
- 候補の絞り込み(あいまい一致)は、**入力済みのディレクトリの中だけ**を対象にする(再帰しない)。階層をまたぐ絞り込みは `C-x p f`(§6)。
- ホストの契約: 入力欄の補完用に、1 階層だけを返す `listDirectory(dir)` を置く。再帰の一覧(`C-x p f`、検索)とは別にする。件数は 2000 件までで、超えたときは打ち切って知らせる。

### 5.1 ディレクトリを開く

`hyperbuf <ディレクトリ>`(CLI、Finder の「このアプリケーションで開く」、ドラッグ&ドロップ、`swift run HyperBuf <dir>` など)は、そのディレクトリの **`index.md`、なければ `README.md`** を開く。どちらもなければ、そのディレクトリで `C-x C-f` の入力欄を開く。

## 6. 一覧と検索の範囲、プロジェクト・ルート

### 6.1 再帰の一覧と全文検索

どちらも、**起点のディレクトリ以下だけ**を対象にする。

- **再帰の一覧 `C-x p f`** と **全文検索 `M-s g` / `C-x p g`** は、起点以下を再帰で走査する。対象は `*.md` とディレクトリだけで、隠しファイルと `node_modules` は除く。`.gitignore` は解釈しない。シンボリックリンクのディレクトリには入らない。
- 守り:
  - `~` と `/` は、再帰の起点として**拒否**する(メッセージを出す)。`C-x p f` では、`C-x C-f` と同じ 1 階層の一覧にして、そう知らせる。
  - 再帰の一覧は、ファイル数 20000 件、時間 3 秒を**上限**とする。検索の結果は 200 件までで、超えたら打ち切って、そう知らせる。
  - **キャンセルできる**(`C-g`)。
  - 外付けディスクやネットワークボリュームでは、列挙の**タイムアウト**で止まらないようにする。
- **任意のファイルに届く:** `C-x p f` の入力に `../`、`~/`、絶対パスを打つと、起点がそのディレクトリに切り替わり、その下を再帰で一覧にする(切り替えたあとは、さかのぼらない)。起点の外のファイルも、同じ入力欄で開ける。選んだ(打った)ファイルは、`C-x C-f` と同じく、アクセスの判定をしない。
- 一覧は、起点からの相対パスで表示する。

### 6.2 プロジェクト・ルートの考え方

Emacs の `project.el` と同じく、**プロジェクトは、バッファから求める「ルートのディレクトリ」にすぎない**。選んだり、開いたり、切り替えたりする状態は持たない。

- **フレームとの対応はない。** フレームは、独立した作業場であって、プロジェクトに結びつかない。同じフレームに、異なるプロジェクトのバッファがあってよい。プロジェクトは、バッファを通してだけ、フレームと関わる。
- 保存するもの(セッション、設定)に、プロジェクトは現れない。ルートは、そのつど、バッファのファイルのパスから計算する。バッファにルートを保存せず、キャッシュも持たない(さかのぼりの回数は、パスの深さだけ)。

### 6.3 ルートの求め方

バッファの基準のディレクトリ(§4)から、親へさかのぼり、**最初に VCS の目印があるディレクトリ**を、ルートにする。

1. 目印: `.git`(ディレクトリ、またはファイル。worktree・submodule)、`.hg`、`.svn`、`.bzr`、`_darcs`、`.jj`。
2. さかのぼりは、**`~` と `/` に達したら止める**(その手前までで、目印がなければ、見つからなかったことにする)。`~` 自体が dotfiles のリポジトリでも、ホスト全体がルートにならない。基準のディレクトリが `~` や `/` 自身のときも、同じく見つからなかったことにする。
3. 無視リスト(§6.4)にあるディレクトリは、目印があっても、ルートにしない(飛ばして、さらに上へ)。
4. **見つからなかったときは、基準のディレクトリ自身をルートにする。** `~/Downloads/notes/` のように、フォルダを切っただけで VCS がない場所でも、その中を一覧・検索できる。
5. §6.1 の守り(`~` と `/` は再帰の起点にしない。件数・時間の上限、`C-g`、タイムアウト)は、**ルートに対しても、そのまま適用する**。たとえば `~` が基準でルートになったときは、1 階層の一覧にして、そう知らせる。

仮想バッファのルートは、その基準のディレクトリ(§4)から、同じ規則で求める。

### 6.4 無視リスト(`projectIgnorePaths`)

安全のため、**ルートにしないディレクトリ**を設定できる。

```json
{
  "projectIgnorePaths": ["~/work/wrapper"]
}
```

- 絶対パス、または `~/…` で書く。シンボリックリンクは解決して照合する。**完全一致**(そのディレクトリ自身だけ。下のディレクトリには効かない)。
- 一致したディレクトリは、目印があっても飛ばし、さらに上をさがす。最後まで見つからなければ、§6.3 の 4 のとおり、基準のディレクトリ自身になる。
- **既定は空**(`~` と `/` は、§6.3 の 2 で、組み込みで除く)。`warnPaths` と同様に、書いたら一覧全体を指定する。
- 不正な値(相対パス、型違い)は、無視して、理由を `C-h b` の「設定の問題」に出す。

### 6.5 ホストの契約

ファイルシステムを見るのは、シェル側の役割。

- `host.projectRoot(dir): Promise<string>`(絶対パスで返る。見つからなければ、`dir` 自身)。Swift 側は、`HyperBufKit` の専用の型(`ProjectRoot`)が担当し、単体でテストできる。
- 目印の確認は、メタデータの確認だけで、ファイルの中身は読まない(アクセスの判定は、通さない)。

### 6.6 コマンド

| キー      | コマンド                   | 動作                                                                                                                 |
| --------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `C-x p f` | `project-find-file`        | **ルート以下**の `*.md` を再帰で一覧にする(§6.1)                                                                     |
| `C-x p g` | `project-find-regexp`      | **ルート以下**の全文検索(結果は仮想バッファ `*search: …*`)                                                           |
| `C-x p b` | `project-switch-to-buffer` | **現在のフレームのバッファのうち、現在のバッファと同じルートのもの**だけを候補にして、`C-x b` と同じように切り替える |
| `C-x p k` | `project-kill-buffers`     | 同じ範囲のバッファを、まとめて閉じる。**閉じる件数を示して、確認する**(`y/n`。1 件でも確認する)                      |

- 入力欄のプロンプトに、ルート(`~/` 形式に短縮)を示す。例: `Find file in ~/work/foo/: `。
- キーは、`keybindings` 設定(個別の割り当て)で変えられる。`C-x p` 専用の仕組みは、持たない。
- **作らないもの:**
  - `C-x p p`(`project-switch-project`)と `C-x p K`(`project-forget-project`)。切り替える状態がなく、編集の作業もしないため、価値が小さい。
  - `C-x p r`(置換)、`C-x p c`(コンパイル)、`C-x p s` / `C-x p e` / `C-x p !` / `C-x p &`(シェル)、`C-x p v`(VC)、`C-x p D`(Dired)。閲覧専用・外部コマンドの非実行の方針による。
  - `C-x p F` / `C-x p G`(外部も含む)。`C-x p f` が外部のディレクトリへ届くので不要。
- `C-x p d`(`project-find-dir`)は未決(§10)。

### 6.7 `M-s g` と `C-x p g`

- `M-s g`(`search-project`)は、**基準のディレクトリ(`default-directory`)以下**を検索する。ルートには寄せない。`C-x p g` は、**ルート以下**を検索する。範囲の狭い検索と広い検索の、両方をキーで選べる。
- 同じ実装(`host.search`)を使い、起点だけが違う。除外(隠しファイル、`node_modules`)・上限・打ち切りは、共通。
- 検索は、固定の文字列の検索で、正規表現は未対応。`project-find-regexp` という名前だが、`M-x` の説明にそう書く。`.gitignore` を読まないことも、`M-x` の説明に書く。

### 6.8 バッファごとのルートとフレーム

- `C-x p b` / `C-x p k` の「同じルート」は、各バッファのパスからルートを求めて比べる。バッファが移動・削除された場合も、パスの親を見る。バッファの数は少ないので、コストは問題にならない。
- **対象は、現在のフレームのバッファだけ。** バッファはフレームごとに持つ(§7)。Emacs の `project-kill-buffers` が、全フレームを見るのとは異なる。

## 7. バッファとフレーム

Emacs のフレーム(macOS のウィンドウ)を複数持てる。並行する仕事ごとに、フレームを分ける使い方を想定する。

- **1 フレーム = 1 つの `NSWindow` + 1 つの WKWebView + 1 つの Web コア。** 各フレームは、自分のバッファ、最近使った順、参照履歴、window の分割、ミニバッファを持つ**独立した作業場**。JS のモデルは WebView をまたいで共有できないので、フレーム間の状態の同期はしない。
- したがって、`C-x b` の候補は、そのフレームで開いたバッファだけ。同じファイルを複数のフレームで開いてもよい(内容は、フレームごとに別々に持ち、ファイルの更新は、各フレームが検知する)。
- **切り替え:** `Cmd-1`、`Cmd-2`、`Cmd-3` … で、対応するスロット番号の**開いている** フレームを前面に出す。Window メニュー(macOS の流儀)に、開いているフレームの項目(`HyperBuf [N]`、前面のものに印)を並べ、そのショートカットとして実装する。WebView にフォーカスがあっても効く(Emacs 側のキーと衝突しない)。開いていない番号では、何も起きない(メニューにも項目がない)。専用の Frame メニューは持たない。
- **スロット番号は固定。** フレームを閉じても、他のフレームの番号は変わらない(フレーム 2 を閉じても、フレーム 3 は `Cmd-3` のまま)。新しいフレームは、空いている最小の番号を使い、`File > New Frame`(`Cmd-N`)か `C-x 5 2` で作る。
- Emacs の操作に合わせたキーを用意する: `C-x 5 2`(フレームを作る)、`C-x 5 o`(次のフレームへ)、`C-x 5 0`(このフレームを閉じる)、`C-x 5 1`(ほかのフレームを閉じる)。Web コアは、ホストの契約(`host.frames`)を通して操作する。
- **外部からの「開く」要求**(CLI、Emacs、URL スキーム)の行き先は、**最後にアクティブだったフレーム**。
- **「エディタで編集」で記録した位置**(`get-location`)と `get-view` は、記録した、または最後にアクティブだったフレームのものを返す。
- **記憶した許可パス**([file-access.md](file-access.md) §4)と設定は、全フレームで共有する(ホスト側で管理する)。
- メモリ: WebContent は、フレームごとに別々のプロセスで、共有されない。実測では、**フレームを 1 つ増やすごとに約 140〜150 MB 増える**(1 フレーム約 190 MB、5 フレーム約 740 MB、8 フレーム約 1.2 GB)。3〜5 フレームの使い方なら許容できるので、この構成を採用している([poc-frames-results.md](../history/poc-frames-results.md))。

## 8. ファイルの内容の変更への追従

監視が必要なのは、**いま window に表示している文書の内容の更新**だけ。`C-x C-f` の候補、`C-x p f` の一覧、検索は、呼ばれたときに走査するので、監視しない。

- **方式:** 表示中の各ファイルと、その親ディレクトリを `DispatchSource`(kqueue)で監視する。**非再帰**なので、ビルド中のリポジトリの直下の文書や、`~` 直下の文書でも、雑音が届かない。待機中の負荷はない(`~` 配下を FSEvents で 20 秒間数えたところ、イベントは約 9 件/秒。リポジトリの直下では、`.build/` や `node_modules/` の更新で増える)。
- **イベントの扱い:** ファイルまたは親ディレクトリのイベントを、短く(約 50ms)まとめて、パスを `stat` し直し、既存の `FileFingerprint` と比べる。変わっていれば、読み直して、閲覧位置を保ったまま描画し直す。保存方式(一時ファイルへ書いて置き換える、元を改名して新しく書く)で inode が変わったら、新しいファイルに監視を張り直す。
- **表示していないバッファは、監視しない。** macOS の GUI プロセスの fd の既定の上限は 256 で、セッションの復元で読み込む文書は数百になりうるため。表示するとき(`C-x b`、Back / Forward、復元)に、ファイルを読み直し、内容が違えば更新する(ホストの契約は変えず、`readFile` を使う)。
- **安全網:** アプリがアクティブになったとき(他のアプリから戻ったとき)に、表示中の文書をもう一度照合する。ネットワークファイルシステムや iCloud で、kqueue のイベントが届かない場合の保険。完全な追従までは求めない。
- **ファイルが削除されたとき:** 表示中のバッファは**閉じずに残し**、ウィンドウのモードラインに `(deleted; it may have been moved)` と出す。同じパスにファイルが再作成されたら(置換保存など)、自動で読み直す。移動は、削除と同じ扱い(追跡しない)。
- 監視の対象は、ウィンドウが表示を替えたら(別の文書へ移る、ウィンドウを閉じる)、外す。同じファイルを複数のフレームが表示するときは、ホスト側で重複を避ける。

### 8.1 移動を追跡しない理由

表示中のファイルが移動・改名されたとき、新しいパスを追って表示を続ける機能は、持たない。fd から現在のパスを `fcntl(F_GETPATH)` で取れるので、技術的には可能だが、次の理由による。

- 保存方式によっては、移動に見えるだけの動きがある(元のファイルを `foo.md~` に改名して、新しく書く方式)。誤って別のファイルを追うおそれがある。
- ゴミ箱への移動は「削除」の意図で、追ってはいけない。移動先が警告パスなら、判定もやり直す必要がある。
- 追うには、全ウィンドウの履歴、最近使った順、セッション、選択範囲のパスを、まとめて付け替える処理が要る。ディレクトリごとの移動では、表示中でない文書は追えず、中途半端になる。
- 今の方針(削除として残し、`C-x C-f` で開き直せる)で、実用上の困りごとは小さい。

AI エージェントによる文書の再配置が多いなど、必要が出てから検討する。

## 9. セッション(バッファの永続化)

- セッションは、全体で 1 つのファイル(プロジェクトごとではない)に、**フレームの並び**として保存する。保存先は `~/Library/Application Support/HyperBuf/session.json`(0600)。
- 起動時は、前回の全フレームを復元する。保存がない・壊れていれば、スロット 1 のフレームが 1 つだけの、空の画面に「`C-x C-f` で開く」と出す。
- `hyperbuf <ファイル>` で開いたときは、復元した状態に、そのファイルを開く(行き先のフレームは、§7)。
- 復元の範囲・保存の動き・壊れたデータの扱いは、[session-restore.md](session-restore.md)。

### 9.1 形式(version 2)

```json
{
  "version": 2,
  "active": 1,
  "フレーム": [
    {
      "slot": 1,
      "rect": { "x": 0, "y": 0, "width": 1200, "height": 800 },
      "snapshot": { "...": "1 フレーム分の配置・履歴・閲覧位置など" }
    }
  ]
}
```

- `snapshot` は、1 フレーム分の状態(配置・履歴・閲覧位置・選択中の window・最近使った順・選択範囲)。
- `rect` は、ウィンドウの位置と大きさ。復元時に、画面の外にならないよう、現在の画面に収まる位置に補正する。
- `active` は、最後にアクティブだったフレームのスロット。
- **フレームを閉じたとき:** 最後の 1 つでなければ、そのフレームのセッションは破棄する(Emacs の `delete-frame` と同じ)。最後の 1 つを閉じる、またはアプリを終了するときは、その時点の全フレームを保存する。
- 保存は、フレームごとの遅延書き込みを、ホストが集めて、1 つのファイルに書く。壊れたフレームは、そのフレームだけ捨て、ほかは復元する。

## 10. 設計判断と未決事項

**プロジェクトという単位を持たない理由。** HyperBuf は、多数の相互参照する文書を、キーボードで行き来するためのビューアである。文書は、1 つのプロジェクトの中に閉じず、リンクはプロジェクトの外にも張られる。「プロジェクトを開く」操作と、それに結びつく設定・セッション・アクセス範囲は、この読み方の邪魔になる。そこで、Emacs と同じく、バッファの場所を基準とし、プロジェクトは必要なときだけ、バッファから計算する。

**決めていないこと:**

- `C-x p d`(`project-find-dir`)の扱い。ディレクトリを選んだときに `index.md` / `README.md` を開く規則(§5.1)との整合を、決めてから入れる。
- `.gitignore` の簡易版の対応。ルート直下の `.gitignore` だけを読む簡易版(`!` と `**` は扱わない)を検討する。ビルド出力や vendor の `.md` が混ざるという声が増えたら、検討する。
- 外部からの「開く」要求で、フレームを指定する方法(`--frame N`、`--new-frame`)。後から足す。

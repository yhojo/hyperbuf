# アーキテクチャ評価(PoC前)

状態: **Draft** — 本文書は PoC 前の仮説整理であり、技術選定を確定するものではない。「仮説」と書かれた項目は PoC で検証する。

## 1. 優先順位

ユーザー合意済みの方針(2026-10-08)。

| 項目 | 方針 |
| --- | --- |
| 基本方針 | **macOS統合を優先**する |
| 他OS展開 | 今は不要だが、**可能性は残したい**(選択肢を閉じない) |
| 特に重視する評価軸 | **操作遅延・応答性** |

README の評価軸(表示互換性、操作遅延、メモリ、拡張性、セキュリティ、macOS統合、保守性、配布容易性)のうち、上記以外は「基準を満たす」ことを条件とし、トレードオフ時の優先度は上の方針に従う。

## 2. 論点の整理

候補は「アプリシェル」と「レンダリング」で分けて考える。

- macOS では **Tauri 2 と SwiftUI+WKWebView はどちらも WKWebView を使う**ため、WebView 内の表示結果は同じ系統になる(仮説)。違いは、シェルの言語、キーイベントの経路、IPC、他OS展開の道筋にある。
- Electron は Chromium を同梱するため表示は一貫するが、メモリ・起動の重さが応答性重視の方針と相性が悪い(仮説)。
- Markdown→HTML の変換と表示を **シェルから独立した Web バンドル**として作れば、シェルの選択を後から変えやすい。README の「疎結合」とも整合する。

## 3. 候補の比較(仮説)

| 観点 | SwiftUI/AppKit + WKWebView | Tauri 2 (Rust) | Electron |
| --- | --- | --- | --- |
| macOS統合 | 最も高い。ネイティブのキー処理・メニュー・ファイル監視を直接使える | WebView は同じだが、統合は Rust 経由・プラグイン経由 | 一通り可能だが、ネイティブ感は劣る傾向 |
| 操作遅延・応答性 | キー入力をネイティブ側で受けられる。WebView への橋渡しコストは要計測 | キーはWebView内で処理するのが基本。Rust側との往復コストは要計測 | Chromium の描画は安定だが、全体に重め |
| メモリ・起動 | 軽い見込み | 軽い見込み | 重い見込み |
| 表示互換性 | WKWebView 依存(Safari系エンジン) | 同左(macOS) | Chromium で最も予測しやすい |
| 他OS展開 | シェルは書き直し。Webバンドルは再利用可 | WebView2/WebKitGTK 経由で道がある | 容易 |
| 開発・保守 | Swift と JS/TS の2言語 | Rust と JS/TS の2言語 | JS/TS 中心 |
| 配布 | 標準的(署名・公証は必要) | 標準的 | サイズ大 |

「ネイティブ描画のみ(WebView 不使用)」は、GFM・Mermaid・数式の再現性を自前で担保する負担が大きいため、候補から外す。

## 4. 暫定の見立て

結論ではなく、PoC の出発点としての見立て。

1. 方針(macOS統合優先、他OSの可能性は残す、応答性重視)に最も合うのは **SwiftUI/AppKit + WKWebView** と **Tauri 2** の2案。Electron は優先度が低い。
2. 両案とも、**レンダリングを Web バンドルとして切り出す**設計にすれば、評価結果が共有できる。
3. 差が出るのは **キーイベントの経路**(ネイティブで受けて WebView に渡すか、WebView 内で処理するか)と、**buffer/window モデルをどちらの層に置くか**。ここが Interaction PoC の主題になる。

## 5. PoC で確かめること

| 問い | 測る・見るもの |
| --- | --- |
| 打鍵から画面反映までの遅延は、ネイティブ受け/WebView内処理でどう違うか | キー入力→スクロール/分割の反映時間 |
| `C-x` 等のチョードが macOS 標準ショートカットや WebView の既定動作と衝突しないか | 衝突するキーの一覧 |
| WebView 内のテキスト選択・検索入力と、キーバインドを両立できるか | 入力欄フォーカス時の挙動 |
| 数百ファイルのプロジェクトでも応答性を保てるか | 一覧表示・全文検索・文書切替の時間 |
| レンダリング Web バンドルを2つのシェルで共有できるか | 同一バンドルでの表示差 |

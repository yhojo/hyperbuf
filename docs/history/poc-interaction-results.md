## 1. 目的と範囲

`architecture-evaluation.md` の問い「SwiftUI+WKWebView と Tauri 2 のどちらがよいか」に対し、`interaction-model.md` の操作モデルを同一の Web コアで実装し、2つのシェルで比べた。Electron は優先度が低いため対象外。

| ブランチ | 内容 | コミット |
| --- | --- | --- |
| `poc/interaction-web` | 共有 Web コア(操作モデル・キー処理・最小描画・サンプル文書・ユニットテスト) | `278ba60` |
| `poc/swiftui-wkwebview` | SwiftUI + WKWebView シェル(上記から派生) | `758d5a0` |
| `poc/tauri-shell` | Tauri 2 シェル(上記から派生) | `7ad84e8` |

共通の設計:

- シェルとの境界は `window.hyperbufHost`(`listFiles` / `readFile` / `onFileChanged`)の3関数のみ。Web コアは**2つのシェルで無変更**。
- ファイルアクセスはプロジェクトルート内の `.md` に限定。外部通信は CSP で遮断(Swift: `connect-src 'none'`、Tauri: IPC のみ)。
- 外部更新の検知は、どちらも 0.5 秒ごとの更新日時の比較(簡易実装)。本番では FSEvents 等を検討する。
- 計測は、キーイベントの発生時刻から、描画後(`requestAnimationFrame` の後)までの時間。物理キーの入力から画面表示までの全遅延ではない。
- どちらも debug ビルドで操作した。

## 3. 遅延

ユーザーの観測値(目視)。

| 操作 | SwiftUI+WKWebView | Tauri 2 |
| --- | --- | --- |
| 多くの操作 | 約 4〜7 ms | 約 5〜9 ms |

- 数値は Tauri が数 ms 遅いが、体感では区別できなかった。どちらも 1 フレーム(約 16.7 ms)の目安に近いか、それ以下に収まっている。
- 差の要因は特定していない(ウィンドウサイズ、debug ビルド、WebView 設定などが候補)。今回は検証していない。

## 5. 分かったこと

1. **Web コアはシェルに依存しない。** 同一コードが2シェルで動き、README の「疎結合」という方針が実証できた。シェルの選択は、コアを書き直さずに後から変えられる。
2. **WKWebView 上の Emacs 風キー操作は成立する。**
   - `keydown` で `preventDefault` すれば、`C-f` / `C-b` / `C-n` / `C-p` / `C-v` などの既定動作を抑止できる。
   - 入力欄にフォーカスがあるときは、既定の文字移動(`C-a` / `C-e` / `C-f` / `C-b`)をそのまま使える。ミニバッファ方針と整合する。
   - `Option` 修飾は、`event.code` から文字を求めれば取得できる(`event.key` は別の文字に変わる)。
3. **コマンドの実行は直列にする必要がある。** ファイル読み込みなどの非同期コマンドの完了前に次のキーが処理されると、分割時の履歴複製などの順序が壊れる。実際にこの不具合が出て、直列化で解消した。
4. **ブラウザの履歴と同様のモデルで、操作は素直に実装できた。** 分割時の履歴複製、window ごとの閲覧位置、`C-x b` を履歴に積む方針、MRU の分離は、いずれも想定どおり動いた。
5. **外部更新の閲覧位置の維持は、見出し基準で実現できる。** 再描画前に画面上端の見出しとのずれを記録し、再描画後に復元する。見出しが消えた場合は、スクロール比率にフォールバックする。長い文書や大幅な変更での精度は、別途の検証が必要。

## 6. 決定

方針(macOS 統合を優先、他OS展開の可能性は残す、応答性を重視)に照らした評価。

| 観点 | 評価 |
| --- | --- |
| 応答性 | どちらも十分。Swift が数 ms 速いが、体感差はない。 |
| macOS 統合 | Swift が優位(メニュー、FSEvents、ネイティブのウィンドウ機能、URL スキーム、将来の CLI/Emacs 連携の受け口を直接扱える)。 |
| 他OS展開 | Tauri が優位。ただし Web コアが共通なので、Swift を選んでも、他OSではシェルだけを作り直せば足りる(今回の規模なら小さい)。 |
| 開発・保守 | どちらも2言語。Swift はビルドが速く、追加の依存がない。 |

**決定(2026-10-08、ユーザー合意): macOS 向けシェルは SwiftUI + WKWebView とする。**

理由:
- macOS 統合を優先する方針に合い、応答性が同等以上で、ビルドや依存が軽い。
- 他OSへ移植する場合は、**そのプラットフォームに最適なフレームワークでシェルを書く**(例: Windows なら C# 系)。クロスプラットフォーム基盤を共有すると、各OSの微妙なバグに悩まされる経験則がある。レンダリングを担う Web コアは分離済みで、シェルとの境界は `hyperbufHost` の契約(3関数)に絞ってあるため、移植の難度は高くない。

前提として守ること:
- Web コアはシェルに依存させない。シェルとの境界は `hyperbufHost` の契約に限る。
- 他OSの移植が具体化した時点で、その OS のシェルを個別に評価する。

Tauri 2 の PoC(`poc/tauri-shell`)は、比較の記録としてブランチを残す。

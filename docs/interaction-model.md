# 操作モデル(buffer / window / frame / 参照履歴)

状態: **Draft** — UI・技術選定に依存しない論理モデルの提案。「提案」は合意前、「未決」は PoC または議論で決める。

## 1. 目的

Interaction PoC で検証するモデルを先に言語化する。実装技術(`architecture-evaluation.md` 参照)から独立させ、どの層にモデルを置くかは PoC の結果で決める。

## 2. 用語とモデル

| 概念 | 定義(提案) |
| --- | --- |
| Project | ルートディレクトリを持つ閲覧の単位。buffer の名前空間。 |
| Buffer | 1つの Markdown ファイルの内容と派生データ(見出し構造、レンダリング結果)。通常は**ファイルと 1:1**。ファイルを持たない**仮想 buffer** もある(§5b)。表示位置は持たない。 |
| Window | 分割ツリーの葉。**1つの buffer を表示**し、閲覧位置(スクロール・アンカー)と**参照履歴**を持つ。 |
| Frame | macOS の 1 ウィンドウに相当。分割ツリーと「選択中の window」を持つ。 |

関係:

```
Project ─┬─ Buffer* (ファイルごとに1つ)
         └─ Frame* ── 分割ツリー ── Window* ──→ Buffer (参照)
                                       └─ 閲覧位置 + 参照履歴 (window固有)
```

- 同じ buffer を複数の window に表示できる。閲覧位置は window ごとに独立する。
- 分割ツリーのノードは「分割(方向・比率・子)」または「window(葉)」。`C-x 2/3` は葉を分割に置換し、`C-x 0/1` は葉を除去する。
- window の大きさ(分割の比率)は、`C-x ^`(縦に広げる)・`C-x }`(横に広げる)・`C-x {`(横に狭める)・`C-x -`(`shrink-window-if-larger-than-buffer`: 文書より大きい window を、文書がちょうど収まる高さまで縮める。文書のほうが大きければ何もしない)、または、モードラインのドラッグ(本体はその下の境界(縦のみ)、右端は右の境界(横のみ)。Emacs と同じ)で変える。1 回の操作の量は、縦 48px・横 80px(プレフィックス引数は未対応)。比率はセッションに保存される。
- 外部連携(CLI・Emacs)の位置つき `open` が、表示中の文書を指すときは、参照履歴を積まず、位置だけを置き換える(Emacs の `goto-line` と同じ)。別の文書なら、通常どおり履歴に積む。モードラインには、バッファ名だけを出す(アンカーは出さない)。
- 閲覧は編集を伴わないため、Emacs の buffer が持つ point/mark/変更状態は持たない。

## 3. Buffer のライフサイクル(提案)

- 初めて開かれたときに作成される。同じファイルを再度開いても、既存 buffer を再利用する。
- どの window にも表示されていない buffer も、明示的に閉じる(`C-x k` 相当)までは保持する。
- ファイルの外部更新を検知したら buffer の内容を更新し、その buffer を表示する各 window は**閲覧位置を可能な限り維持**する(README の開発連携要件)。
- `C-x b` の候補は、最近使った順(MRU)に並べる。この順序は参照履歴とは別に管理する。
- ファイルが削除された場合は、buffer を「ファイルなし」の状態で残し、履歴からの復帰先として扱う。

## 4. 閲覧位置

Window は次のいずれかで位置を表す。

- **アンカー**: 見出し ID など、文書内の意味的な位置。
- **スクロールオフセット**: アンカー内の相対位置。

再読み込み後は、アンカーが残っていればそれを基準に復元し、消えていれば直前のオフセット比率にフォールバックする(提案)。

## 5. 参照履歴(Back / Forward)

方針: Back / Forward は参照履歴の前後移動。buffer 切替も参照として履歴に積む。`C-x b` の候補順(MRU)は参照履歴とは別に管理する(変更の経緯は `plan-change-log.md`)。

### 5.1 構造(提案)

- **window ごと**に、ブラウザの履歴と同じ「列 + 現在位置」を持つ。
- エントリは `{buffer, アンカー, スクロールオフセット}`。
- Back した後に新しい参照を行うと、現在位置より先のエントリは破棄する(ブラウザと同じ)。

### 5.2 エントリを積む操作(提案)

| 操作 | 履歴に積む |
| --- | --- |
| 文書内リンク・文書間リンクをたどる | 積む |
| 見出しジャンプ(アウトライン) | 積む |
| 全文検索の結果から開く | 積む |
| `C-x b` / `C-x C-f` で別の buffer を表示 | 積む(合意済み) |
| 通常のスクロール | 積まない(現在エントリの位置だけ更新) |
| 文書内検索(`C-s`) | 積まない |

### 5.3 window 分割時の履歴(合意済み)

新しい window に、分割元の履歴を複製する(ブラウザのタブ複製に近い)。以降の履歴は window ごとに独立する。

### 5.4 Back / Forward のキー(合意済み)

- **`C-b` / `C-f`** を Back / Forward とする。編集における C-f/C-b が「文字の流れ」を泳ぐ操作であるのと同様に、HyperBuf では「参照の流れ」を泳ぐ操作として再利用する。
- `Cmd+[` / `Cmd+]` を macOS 向けの別名として併用する。
- カーソルキーの `←` / `→` も、別名として割り当てる(Emacs に不慣れな利用者のため。修飾キーつきは、割り当てない)。
- 縦方向の移動(C-n/C-p/C-v/M-v)は文書内(空間)、C-f/C-b は参照の流れ(時間)と使い分ける。
- `C-c` 系プレフィックスは、markdown-mode の outline-mode 風カーソル移動のために予約し、Back / Forward には使わない。
- `M-f` / `M-b` は予約する。案: 同じ文書内のアンカー移動を飛ばして、前後の別の文書へ進む・戻る(Emacs の C-f→M-f のように、修飾キーで単位が広がる)。未決。

### 5.5 未決事項

- **履歴の粒度。** 同一文書内の連続したアンカー移動を 1 エントリにまとめるか。
- **履歴の上限と永続化。** セッション復元と合わせて検討する。

## 5b. 仮想 buffer と行アンカー(合意済み)

Project navigation PoC(`poc-navigation-results.md`)の結果を取り込む。

### 仮想 buffer

- **ファイルに対応しない buffer。** 内容はアプリが生成する。名前は `*…*`(Emacs の `*grep*` や `*Help*` と同じ慣習)。例: 検索結果 `*search: クエリ*`。将来の例: 目次、履歴の一覧、エラー表示。
- 通常の buffer と同じ扱い。window に表示でき、参照履歴に積まれ、Back / Forward で行き来でき、`C-x b` の候補(MRU)にも出る。内容中のリンクで、実ファイルへ飛べる。
- ファイル監視の対象外。同じ名前で再生成すると、内容が置き換わる(再検索)。
- 結果画面のための専用の仕組みを作らず、既存の操作モデルに乗せることが目的。

### 行アンカー

- `path#line:N` は、元の Markdown の N 行目(以前で最も近いブロック)を指す。見出しのアンカー(`path#見出し`)と同じ経路で開く。
- 検索結果からの該当行へのジャンプに使う。将来の CLI・Emacs 連携の「ファイルと行を指定して開く」は、この行アンカーの上に作る。

## 6. 入力とコマンド

- 操作はすべて**名前付きコマンド**として定義し、キーマップはキー列→コマンドの対応とする。`M-x` はコマンド名で実行する。
- プレフィックス(`C-x` など)は状態機械で扱う。入力待ち中は画面に途中経過を表示する。
- 検索や `C-x b` の候補選択、`M-x` などの入力は、**ダイアログを出さず frame 下部のミニバッファで行う**(合意済み)。
- ミニバッファにフォーカスがあるときは、その入力用のキーマップを優先する。C-f/C-b などは文字移動に戻り、コマンド用キーとテキスト入力を競合させない(Emacs のミニバッファと同じ振る舞い)。
- キーマップはユーザーが変更できる。macOS 標準ショートカットとの衝突は PoC で一覧化する。

### 6.1 ミニバッファと日本語入力(IME)(M3 の手動確認で判明)

WKWebView の入力欄(`<input>`)で日本語を変換しながら、インクリメンタル検索を使うときの注意。自動テストの合成イベントでは再現できず、実機で見つかった。

- **確定の Enter は `keyCode 229` で届く**(WebKit では、確定のあと)。これを `RET` として扱うと、確定と終了が同時に起きる。`isComposing` または `keyCode 229` の Enter / ESC は、ミニバッファでは無視する(Ctrl・Meta・Alt 付きは対象外)。変換中の Enter は確定だけを行い、次の Enter で終了する。
- **確定のとき、入力が「空 → 確定した文字列」の順で、二度届く**。「いまの一致」の記憶を検索語に結びつけると、空の瞬間に消えて、先頭の一致に戻る。探し直す基準の位置は、検索語とは別に保持する。
- **変換中の入力(`InputEvent.isComposing`)では、基準の位置を動かさない**。ローマ字入力の途中の「さ」の一致に引きずられると、変換後の語を、その位置より後ろから探してしまう。
- **文書に選択を作る・消すと、入力欄のフォーカスが外れる**(WKWebView)。入力中のハイライトは CSS Custom Highlight API だけで描き、選択は、確定のあとに作る。

### 6.2 `count-words`(`M-=`)【決定】

選択範囲(なければ文書全体)の、行・単語・文字の数を、エコー領域に出す(2026-10-14)。

- 例: `Region has 3 lines, 42 words, 210 characters (180 without whitespace)`(選択なしは `Buffer has …`)。
- **数える対象は、表示されているテキスト(描画後)**。元の Markdown ではない。ビューアなので、見た目を優先する。Markdown の記号や URL、画像、図(SVG)は数えず、コードブロック・表のセル・リンクの文字・数式は数える。元の Markdown の数は、Emacs の `count-words` で測る。
- 行は、空でない行の数(段落・リスト項目・表の行・コードの行が、それぞれ 1 行)。単語は、`Intl.Segmenter` の単語分割(日本語などは、辞書による分割)。文字は、コードポイントの数で、行の区切りの改行を 1 つとして含み、空行は含めない。括弧の中は、空白(改行を含む)を除いた文字の数。
- **選択中の字数を、モードラインにリアルタイムで出す機能は、実装しない。** 最小限の UI で十分、という Emacs の文化に沿った判断。必要なときに、`M-=` で数える。

## 6b. UI の言語と、macOS / Emacs の使い分け【決定】

v0.1.0 の初期配布で出たフィードバック(メニューやモードラインの日本語への違和感、macOS のメニューの流儀)を受けて決めた(2026-10-14)。

**UI の文言は、英語に固定する(ローカライズしない)。**

- 対象は、アプリが出す文言のすべて: メニュー、モードライン、エコー領域、ミニバッファのプロンプト、コマンドの説明(`M-x`・`C-h b`)、確認・エラーの文、CLI の usage とエラー、Emacs パッケージ(`emacs/`)のメッセージと docstring。
- 理由: Emacs の語彙(buffer / window / frame / mode line / minibuffer / echo area)は英語で、キーやコマンド名とも揃う。検索して、世界中の知見を共有しやすい。二言語の文言を保守しない(小さな体制で、ずれが出ない)。
- **扱う内容(文書の本文、ファイル名、アンカー、検索語、ミニバッファでの入力)は、国際化されている**(日本語を含む。§6.1)。固定するのは、アプリ自身の文言だけ。
- `.lproj` / `.strings` / `NSLocalizedString` は使わない。新しい文言は、最初から英語で書く(日本語の文言を直書きしない)。
- OS が出す標準の UI(ファイルを開くパネルなど)は、システムのロケールに従う。

**macOS の流儀と Emacs の流儀を、場所で分ける。**

| 場所                                                           | 流儀       | 具体                                                                                                                                        |
| -------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| メニューバー、ダイアログ、右クリックメニュー                   | macOS      | 標準の構成(App / File / Edit / Window)と標準のショートカット(`Cmd-N`・`Cmd-W`・`Cmd-M` など)。文言は macOS の英語表記(Title Case)           |
| フレーム(macOS のウィンドウ)の切り替え                         | macOS      | 専用のメニューは持たず、Window メニューに、開いているフレームを `Cmd-1`〜`Cmd-9` つきで並べる(前面に印)。開いていない番号では、何も起きない |
| フレームの中(モードライン、エコー領域、ミニバッファ、キー操作) | Emacs      | `C-x …` / `M-x` のキー、コマンド名、用語(buffer / window / frame)。エコーの文は、Emacs と同じ体裁(先頭は大文字、文末に句点を付けない)       |
| 外部との連携(CLI、`hyperbuf://`、Emacs パッケージ)             | 双方の慣習 | CLI は UNIX の慣習(usage、終了コード)。Emacs パッケージは Emacs の慣習(`user-error`、docstring の 1 行目は完結した文)                       |

- 目安: **メニューバーとダイアログは macOS、フレームの中は Emacs。** Cmd キーのショートカットは macOS の標準に使い、Emacs のキー(`C- / M-`)と衝突させない。
- **用語のずれは、受け入れる。** Emacs の frame は、macOS では「ウィンドウ」なので、Window メニューに並ぶのは frame である。メニューは macOS の言葉、ヘルプや文書は Emacs の言葉で書く(利用者は、このずれを理解して、楽しんでいる)。
- 項目の表示(Window メニューの `HyperBuf [N]` など)は、当面、ウィンドウのタイトルと同じ。あるべき形は、引き続き検討する。

**文書(ドキュメント・チュートリアル)の言語【検討中】**

- 利用者向けの文書は、英語を主にする。Emacs の info のように、ロケールに沿った翻訳を後から足す形が望ましいが、予定は決めていない。
- 設計文書(`docs/`)とコードのコメントは、ソースコードの公開の準備(M8)までは、日本語のまま。`emacs/` は、UI に影響するため、先に英語にした。

## 7. Interaction PoC の検証シナリオ

1. 1つの frame を `C-x 2` / `C-x 3` で分割し、`C-x o` で移動、`C-x 0` / `C-x 1` で閉じる。
2. 同じ buffer を 2 つの window に表示し、片方だけスクロールしても他方が動かない。
3. リンクをたどって Back / Forward し、スクロール位置まで復元される。
4. `C-x b` の MRU 順が、参照履歴とは独立している。
5. 外部でファイルを書き換えても、各 window の閲覧位置が維持される。
6. 検索入力中に `C-x` などがテキスト入力と衝突しない。
7. 打鍵から反映までの遅延が体感で問題ない(数値は `architecture-evaluation.md` の計測項目に従う)。

## 8. 範囲外(このPoCでは扱わない)

- 複数 frame と Project の対応(1 frame = 1 project か、project を切替えるか)。
- コピーのためのテキスト選択の方法。閲覧画面へのカーソル表示は導入しない方向で、別途検討する。
- セッション復元の保存形式。
- 拡張機構。
- 見た目の作り込み。

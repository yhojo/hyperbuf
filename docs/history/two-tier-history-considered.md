# 参照履歴の2階層化の検討(採用しなかった案、2026-10-22)

`C-f` / `C-b` と `M-f` / `M-b` の役割を分け、参照履歴を2階層にする案を検討し、**採用しなかった**。ここには、検討した内容と採用しなかった理由を残す。現行の仕様は [interaction-model.md](../dev/interaction-model.md) §4。

設計の下書きは、ブランチ `poc/two-tier-history`(コミット `e1c9ac2`、`docs/dev/interaction-model.md` の §4 と §7)に残してある。`main` にはマージしていない。

## 1. 動機

- `M-f` / `M-b` が未割り当てであることが気になった。
- 当時の `C-f` / `C-b` は、ファイルをまたぐ参照履歴の Back / Forward だった。これを、文書内のスクロールを伴う細かい単位の移動に変え、`M-f` / `M-b` を意味単位(文書や見出しをまたぐ移動)にしたい、という要望があった。
- Emacs では、修飾キーを付けると移動の単位が広がる(`C-f` が文字、`M-f` が単語)。その身体性に沿った一貫性を目指した。
- `C-f` / `C-b` が細かい単位の端に着いたら、その先の単位へ自然に越えていく動きも望まれた。

## 2. 検討した案

**履歴を2階層にする。**

- **エントリ**(粗い単位): リンク、見出しジャンプ、バッファ切替で積む参照。`M-b` / `M-f` で動く。
- **ストップ**(細かい単位): 1つのエントリ内の位置。`C-b` / `C-f` で動き、ストップが尽きたら隣のエントリへ越える。越えた先は、前のエントリなら最後のストップ、次のエントリなら最初のストップとする。
- **ストップの作り方(ジャンプ型)**: Emacs の mark ring に近く、大きな移動の前に、離れた位置を記録する。対象は `C-s` の確定(`C-g` は対象外)、`M-<` / `M->`、`M-g g`、見出し移動。`C-v` / `SPC` / `C-n` やホイールでは作らない。1画面未満の移動も作らない。1エントリあたり最大20。
- **周辺のキー**: `C-a` / `C-e` はエントリ単位のまま。`Cmd+[` / `Cmd+]` は `M-b` / `M-f` の別名、`←` / `→` は `C-b` / `C-f` の別名とする。コマンド名の `back` / `forward` はエントリ単位のまま残し、細かい側には `back-position` / `forward-position` を新設する。

ページ単位(`SPC` ごとに記録する案)は、読み進めるだけで履歴が膨らみ、実質的に逆スクロールになるので、ジャンプ型を選んだ。

## 3. 検討で見えた論点

- **ストップが、ファイルの編集でずれる。** 行番号で持つと、別のエディタで上の行が増減した時点で、別の場所を指す。ピクセル値より安定するのは、ウィンドウサイズの変更に対してだけだった。
- **旧テキストは保持していない。** `Buffer.text` は最新の1つだけで、`WinView.lastText` は表示用に1ウィンドウが持つ。差分で再配置するには、バッファごとに旧テキストを保持するか、別の手段が要る。
- **非表示のバッファは、再表示のときに初めて更新に気づく。** 監視するのは表示中のファイルだけ(kqueue、非再帰)で、非表示のバッファは表示するときに読み直して比べる([buffer-model.md](../dev/buffer-model.md) §8)。
- **設計の方向(下書きの内容)**: 旧テキストを保持せず、ストップに「行、属する見出しの ID と見出しからの行数、行の文脈(空でない最大3行を各80文字まで)」を持たせる。テキストが置き換わるとき、文脈の一致、文脈の探索、見出しからの位置、行を末尾に収める位置の順に再配置する。セッションにも保存する。
- **決め切れなかった数値**: 文脈の行数・文字数、短い行を除く基準。見出し名が変わった場合の扱い。

## 4. 採用しなかった理由

仕様が複雑になりすぎ、利用者が「何が正しいのか」を理解しにくくなる、という指摘を受けた。たとえば次の点を、利用者が把握する必要が生じる。

- 履歴にはエントリとストップの2種類があり、どの操作でどちらが増えるか。
- `[History N/M]` はエントリ数を数え、ストップは数えないこと。
- `C-f` が「次のストップ」と「次のエントリ」のどちらへ動くかは、位置によって変わること。
- ファイルを編集したとき、ストップは近似で再配置され、外れることがあること。

この検討を通して、**現行の仕様が持つ単純さの価値**が見えた。現行の履歴は、文書内のスクロール、検索(`C-s`)、見出し移動(`C-c C-n` など)では変わらない。参照(リンク、名前で選んだ見出しや行、バッファの表示)だけが履歴に積まれる。そのため、長い文書の中で何をしても、`C-b` は「直前の参照に戻る」ことであり続け、戻り先の参照も、進む先のエントリも失われない。履歴に何が入るかは、「文書が指した場所、または読み手が名前で選んだ場所がエントリで、それ以外は読んでいるだけ」という1つの規則で分かる。文書内の位置を履歴に加える案は、この単純さを損なう。これを現行の設計原則として、[interaction-model.md](../dev/interaction-model.md) §4.2.1 に書いた。

実装の側でも、履歴の構造、スクロールの扱い、再配置、セッション形式、旧形式との互換性が一度に増える。得られるのは、細かい位置を戻れる便利さだけで、複雑さに見合わないと判断した。

## 5. 現状

- `M-f` / `M-b` は、**意図的に未割り当てのまま**にする。
- `C-f` / `C-b` は、これまでどおり参照履歴の Back / Forward。
- 履歴の粒度(同一文書内の連続するアンカー移動を1エントリにまとめるか)は、今回の検討とは別の論点として、[interaction-model.md](../dev/interaction-model.md) §7 に残す。
- 細かい位置に戻りたいときは、現状では `C-s`、`M-g g`、見出し移動、Back / Forward を使う。

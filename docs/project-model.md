# ファイルの扱い: プロジェクトを持たない設計

状態: **実装済み(M7b、2026-10-10 完了)**。実装の記録は `docs/migration-plan.md`。

凡例: **【決定】** 合意済み / **【仮】** 仮の値で始め、動作確認で決める / **【将来】** 今は実装しない。

## 1. 方針【決定】

Emacs の流儀に合わせる。**バッファが主役で、基準は「現在のバッファのファイルのディレクトリ」**(Emacs の `default-directory`)。「プロジェクトを選ぶ」操作はない。

- バッファの識別は、**絶対パス**(`realpath` で正規化)。
- ファイルを開く・検索する範囲は、現在のバッファのディレクトリから決まる。
- **「プロジェクト」という、選んだり切り替えたりする単位は持たない**(プロジェクトの設定も、フレームとの対応もない)。ファイルを開く・一覧にする・検索する範囲は、基準のディレクトリから決まる。v0.1.2 で、Emacs の `project.el` と同様の**プロジェクト・ルート**(バッファのファイルから求める、計算上のディレクトリ)を加える([§14](#14-プロジェクト・ルートv012-の設計案))。
- アクセスの安全は、**許可パス / 警告パス**で決める(§5)。
- セッションは、全体で 1 つ。起動時は、前回の状態を復元する(なければ、空の画面)。

## 2. 基準のディレクトリ(`default-directory`)【決定】

| バッファ                       | 基準のディレクトリ                         |
| ------------------------------ | ------------------------------------------ |
| ファイルの文書                 | そのファイルのディレクトリ                 |
| 仮想バッファ(`*search: …*`)    | 検索の起点のディレクトリ                   |
| 仮想バッファ(`*Help: …*` など) | 直前に選択していたバッファのものを引き継ぐ |
| バッファがない(起動直後)       | ホスト(`~`)                                |

ミニバッファを開くときは、開いた時点で選択していたバッファの基準を使う。

## 3. ファイルを開く(`C-x C-f`)

- 入力欄は、基準のディレクトリ(`~/` 形式に短縮して表示)から始まる。【決定】
- 候補は、入力済みのディレクトリの中の **`.md` ファイルとサブディレクトリ**(隠しファイルは、入力が `.` で始まるときだけ)。【決定】
- `~/`、`../`、絶対パスの入力に対応する。`TAB` で補完する。【決定】
- **ディレクトリは、`RET` で確定しない**。ディレクトリを選んで `RET` を押すと、その中に入る(入力欄の末尾が `/` になり、候補が更新される)。【決定】
- **`.md` のファイルを指定したときだけ、開く**。`.md` 以外、存在しないファイルは、メッセージを出して開かない(ビューアなので、新規作成はしない)。【決定】
- 自分で打ったパスは、利用者の意思そのものなので、**警告の判定をしない**(§5)。【決定】
- 候補の絞り込み(あいまい一致)は、**入力済みのディレクトリの中だけ**を対象にする(再帰しない。階層をまたぐ絞り込みは `C-x p f`)。【決定】
- ホストの契約: 入力欄の補完用に、1 階層だけを返す `listDirectory(dir)` を置く。再帰の一覧(`C-x p f`、検索)とは別にする。【決定】
- `listDirectory` の件数の上限は、仮の値(2000 件)で始め、動作確認の中で最終的に決める。超えたときは、打ち切って知らせる。【仮】

`C-x p f`(新規)は、**基準のディレクトリ以下の全文書**を、再帰で一覧にして絞り込む(候補は、基準からの相対パス)。今の `C-x C-f` の動き(全文書から絞り込む)は、これに移す。【決定】

- **任意のファイルに届く:** 入力に `../`、`~/`、絶対パスを打つと、基準がそのディレクトリに切り替わり、その下を再帰で一覧にする。基準の外のファイルも、同じ入力欄で開ける。【決定】
- 選んだ(打った)ファイルは、`C-x C-f` と同じく、利用者の意思なので、警告の判定をしない(§5)。【決定】
- 守りは、検索(§4)と共通: 基準が `~` や `/` のときは、再帰せず、`C-x C-f` と同じ 1 階層の一覧にして、そう知らせる。ファイル数と時間の上限、キャンセル(`C-g`)、タイムアウトも同じ。【決定】
- キーは `C-x p f` のまま(`project.el` の `project-find-file` のサブセットとして使う。【決定】)。

### 3.1 ディレクトリを開く【決定】

`hyperbuf <ディレクトリ>`(CLI、Finder の「このアプリケーションで開く」、ドラッグ&ドロップ、`swift run HyperBuf <dir>` など)は、そのディレクトリの **`index.md`、なければ `README.md`** を開く。どちらもなければ、そのディレクトリで `C-x C-f` の入力欄を開く。

これまでの使い方(プロジェクトのディレクトリを渡して開く)と、統合テストの起動が、そのまま通る。

## 4. 再帰の一覧と検索

どちらも、**基準のディレクトリ以下だけ**を対象にする。

- **再帰の一覧 `C-x p f`**(§3)と、**全文検索 `M-s g`** は、基準のディレクトリ(検索結果の仮想バッファは、その起点)以下を再帰で走査する。【決定】
- 守り【決定】:
  - `~` と `/` は、再帰の起点として**拒否**する(メッセージを出す)。`C-x p f` では、1 階層の一覧にする。
  - 件数(ファイル数)と時間に**上限**を設ける。超えたら、打ち切って、そう知らせる。
  - **キャンセルできる**(`C-g`)。
  - 外付けディスクやネットワークボリュームでは、列挙に**タイムアウト**を設ける。
- **プロジェクト・ルート(v0.1.2):** VCS の目印をさかのぼって root を求める拡張は、§14 に設計案がある。それが入るまでは、上の規則(基準のディレクトリだけ)で動く。
- 一覧と検索の対象は、今までどおり `*.md` と、ディレクトリだけ。隠しファイルと `node_modules` は除く。【決定】

## 5. アクセスの判定(許可パスと警告パス)

### 5.1 判定の対象【決定】

次の経路は、すべて同じ判定を通る(判定は Swift 側の `FileAccess` が行い、Web コアは確認の表示だけを担当する)。

- リンクのクリック
- CLI・Emacs・URL スキームからの「開く」
- 文書が参照する画像などのリソース

`C-x C-f` で打ったパスは、判定しない。

### 5.2 経路による扱いの違い【決定】

URL スキーム(`hyperbuf://open?...`)は、ブラウザ上の任意のページなど、**起点を特定できない**経路から起動できる。パスの規則だけで判定せず、起点で扱いを分ける。

| 経路                                               | 判定                                                                   |
| -------------------------------------------------- | ---------------------------------------------------------------------- |
| ソケット(CLI、Emacs。CLI の初回起動を含む。下の注) | 同一ユーザーのプロセスなので、パスの規則(§5.3)だけで判定する           |
| **URL スキーム**                                   | 許可パスにないファイルは、**警告パスの外でも、ミニバッファで確認する** |
| リンクのクリック、リソース                         | パスの規則(§5.3)だけで判定する                                         |
| `C-x C-f`、ミニバッファで打ったパス                | 判定しない(利用者の意思)                                               |

**注: CLI の初回起動。** 今の CLI は、アプリが起動していないとき、最初のファイルを `hyperbuf://open?...` の URL で渡して起動する。これだと、起動のたびに URL スキームの確認が出てしまうため、Emacs 連携と同じ流れにそろえる: `hyperbuf://ping`(起動だけ)でアプリを起動し、ソケットが現れるまで待ち、ソケットで「開く」要求を送る。CLI と Emacs の要求は、すべてソケットを通る。URL スキームは、起動と外部リンクだけに使う(段階 2 で変更する)。【決定】

### 5.3 パスの規則【決定】

パスを正規化(`realpath`。シンボリックリンクは実体で判定する)したうえで、設定に書かれた**許可パス**と**警告パス**を照合する。

1. どちらにも一致しなければ → **開く**。
2. 一致するものがあれば、**一番長く一致したもの**が勝つ(より具体的な指定が優先)。
   - 許可パスが勝つ → 開く。
   - 警告パスが勝つ → ミニバッファで確認する。
3. 許可と警告が**同じパス**で重なっていれば、安全側の警告にして、設定の問題として報告する。

| 設定                                             | ファイル               | 結果                   |
| ------------------------------------------------ | ---------------------- | ---------------------- |
| `allowPaths: ~/work`、`warnPaths: ~/work/vendor` | `~/work/vendor/x.md`   | 警告(具体的な方が勝つ) |
| `allowPaths: /usr/share/doc`、`warnPaths: /usr`  | `/usr/share/doc/a.md`  | 許可                   |
| (どちらにも一致しない)                           | `~/Downloads/foo/a.md` | 開く                   |

パスの一致は、区切りの境界で判定する(`/tmp` が `/tmp2` に一致しない)。存在しないパスの比較は、大文字小文字を区別しない(APFS)。

### 5.4 確認と記憶

- 警告パスのファイルを開くときは、ミニバッファで確認する(今の「範囲外のファイル」の確認と同じ操作)。【決定】
- 承認すると、そのファイルのディレクトリ以下を記憶し、次からは確認しない(記憶は永続化する。実質は具体的な許可パスとして働く)。【決定】
- **記憶の範囲の制限**【決定】: 記憶するディレクトリが、**警告パスそのもの、またはその上位**になる場合は、ディレクトリではなく、**そのファイル単体**だけを記憶する(`/tmp/x.md` を承認して、`/tmp` 全体が許可になるのを防ぐ)。
- まとめて許可したい場所は、`allowPaths` に書く。【決定】
- 記憶したパスの**一覧と取り消し**のコマンド `M-x forget-remembered-path` を設ける(記憶したパスが候補に出て、`RET` で選んだものを取り消す)。記憶の保存先は、利用者が書く `config.json` とは別のまま(アプリは設定ファイルを書き換えない)。既存の `trusted-roots.json` は、記憶したパスとして引き継ぐ。【決定】

### 5.5 画像などのリソース【決定】

リソースは、文書の描画中に非同期で読み込まれるので、その場で確認を出して止められない。次の流れにする。

1. 描画の**前**に、文書内のローカル画像のパスを集めて、まとめてホストに判定させる。
2. 警告対象のリソースは、読み込まずに、プレースホルダーを出す。
3. 描画のあとに、「警告対象のパスの画像が N 件あります(`<ディレクトリ>`)。許可しますか?」とミニバッファで一度だけ聞く。
4. 確認を出すのは、**アクティブなフレームの選択中の window の文書だけ**(セッションの復元で、複数のフレームが同時に確認を出さないため)。それ以外の文書は、プレースホルダーのまま待ち、その window が選択されたときに聞く。
5. 承認したら、そのディレクトリを記憶し、描画し直す。断った場合は、**そのセッションの間は覚えて**、ファイルの更新による再描画で聞き直さない。
6. 許可・拒否の**最終判定は、スキームハンドラ側で必ず再確認する**(Web コアの判断を信用しない。今と同じ)。

### 5.6 既定値【決定】

- `warnPaths` の既定: `/usr`、`/opt`、`/tmp`、`/var`、`/etc`、`/System`、`/Library`、および、ホスト配下の機微な場所 `~/.ssh`、`~/.aws`、`~/.gnupg`、`~/Library`。
- `allowPaths` の既定: `~/Library/Mobile Documents`(iCloud Drive。`~/Library` の警告より、長い一致が勝つ)。`/Volumes`(外付けドライブ)は、警告に入れない(自分の文書を、毎回確認されないように。代わりに、列挙のタイムアウトで守る)。
- `allowPaths` は、警告パスと重なる場所でだけ意味を持つ(警告パスの下で、確認を省く場所を指定する)。名前は `trustedPaths` から `allowPaths` に改めた。【決定】

macOS では `/tmp`、`/var`、`/etc` が `/private/...` へのシンボリックリンクなので、設定のパスも、読み込み時に正規化して照合する。存在しないパスは、文字列のまま使う。

## 6. 設定(`config.json`)【決定】

```json
{
  "warnPaths": ["/usr", "/opt", "/tmp", "/var", "/etc", "/System", "/Library"],
  "allowPaths": ["~/work", "/usr/share/doc"]
}
```

- `warnPaths` は、書いたら既定の一覧を**置き換える**。`[]` で警告なし。
- `~` は展開する。絶対パスでないもの、型が違うものは、無視して理由を `C-h b` の「設定の問題」に出す。

## 7. セッションと起動【決定】

- セッションは、全体で 1 つのファイル(プロジェクトごとではない)に、**フレームの並び**として保存する(§10)。保存先は、`~/Library/Application Support/HyperBuf/session.json`(0600)。
- 起動時は、前回の全フレームを復元する。保存がない・壊れていれば、スロット 1 のフレームが 1 つだけの、空の画面に「`C-x C-f` で開く」と出す。
- `hyperbuf <ファイル>` で開いたときは、復元した状態に、そのファイルを開く(行き先のフレームは、§10)。
- 移行: M7 のプロジェクトごとのセッションは、破棄する(利用者は作者のみ)。

## 8. ファイルの監視【決定】

監視が必要なのは、**いまウィンドウに表示している文書の内容の更新**だけ。`C-x C-f` の候補、`C-x p f` の一覧、検索は、呼ばれたときに走査するので、監視しない。

- **方式:** 表示中の各ファイルと、その親ディレクトリを `DispatchSource`(kqueue)で監視する。**非再帰**なので、ビルド中のリポジトリの直下の文書や、`~` 直下の文書でも、雑音が届かない。待機中の負荷はない(`~` 配下を FSEvents で 20 秒間数えたところ、イベントは約 9 件/秒。リポジトリの直下では、`.build/` や `node_modules/` の更新で増える)。
- **イベントの扱い:** ファイルまたは親ディレクトリのイベントを、短く(約 50ms)まとめて、パスを `stat` し直し、既存の `FileFingerprint` と比べる。変わっていれば、読み直して、閲覧位置を保ったまま描画し直す(今の仕組みのまま)。保存方式(一時ファイルへ書いて置き換える、元を改名して新しく書く)で inode が変わったら、新しいファイルに監視を張り直す。
- **表示していないバッファは、監視しない。** macOS の GUI プロセスの fd の既定の上限は 256 で、セッションの復元で読み込む文書は数百になりうるため。表示するとき(`C-x b`、Back / Forward、復元)に、ファイルを読み直し、内容が違えば更新する(ホストの契約は変えず、`readFile` を使う)。
- **安全網:** アプリがアクティブになったとき(他のアプリから戻ったとき)に、表示中の文書をもう一度照合する。ネットワークファイルシステムや iCloud で、kqueue のイベントが届かない場合の保険。完全な追従までは求めない。
- **ファイルが削除されたとき:** 表示中のバッファは**閉じずに残し**、ウィンドウのモードラインに `(deleted; it may have been moved)` と出す。同じパスにファイルが再作成されたら(置換保存など)、自動で読み直す。移動は、削除と同じ扱い(追跡しない)。
- 監視の対象は、ウィンドウが表示を替えたら(別の文書へ移る、ウィンドウを閉じる)、外す。

### 8.1 将来の検討: 移動の追跡【将来】

表示中のファイルが移動・改名されたとき、新しいパスを追って表示を続ける機能。fd から現在のパスを `fcntl(F_GETPATH)` で取れるので、技術的には可能。**今は実装しない**。理由:

- 保存方式によっては、移動に見えるだけの動きがある(元のファイルを `foo.md~` に改名して、新しく書く方式)。誤って別のファイルを追うおそれがある。
- ゴミ箱への移動は「削除」の意図で、追ってはいけない。移動先が警告パスなら、判定もやり直す必要がある。
- 追うには、全ウィンドウの履歴、最近使った順、セッション、選択範囲のパスを、まとめて付け替える処理が要る。ディレクトリごとの移動では、表示中でない文書は追えず、中途半端になる。
- 今の方針(削除として残し、`C-x C-f` で開き直せる)で、実用上の困りごとは小さいと見込む。

AI エージェントによる文書の再配置が多いなど、必要が出てから検討する。

## 9. バッファの名前と表示【決定】

バッファの識別は絶対パス(§1)。画面に出す**名前**は、Emacs の `uniquify` と同じ考え方で決める。

- **基本は、ファイル名(basename)**。例: `project-model.md`。
- 開いているバッファの中に**同じ名前が複数あるときだけ**、親ディレクトリを足して区別する。形式は Emacs の既定(`post-forward-angle-brackets`)に合わせ、`名前<区別の接尾辞>`。例: `README.md<docs>`、`README.md<emacs>`。接尾辞は、区別がつく最小の、ディレクトリの末尾側の部分(足りなければ `README.md<a/docs>` のように、上へ伸ばす)。
- 名前は**動的**: バッファが開く・閉じる(`C-x k`)と、衝突の有無が変わり、名前も変わる(Emacs と同じ)。識別は絶対パスなので、履歴・セッション・選択範囲には影響しない。
- プロジェクトという単位は持たないので、名前にも含めない。
- アンカー(`#見出し`、`#line:N`)は、名前には付けない(参照履歴のエントリの位置であって、バッファの名前ではない)。
- **仮想バッファ**(`*search: …*`)は、検索の**起点の短いパス**を添える: `*search: foo*<docs>`(接尾辞の決め方は、ファイルと同じ。起点が `~` なら `<~>`)。検索結果の各ヒットは、起点からの相対パスで表示する。`*Help: …*` は、そのまま。

### 9.1 表示する場所

| 場所                     | 表示                                                      |
| ------------------------ | --------------------------------------------------------- |
| ウィンドウのモードライン | `project-model.md  Top  L1  [History 2/5]`                |
| `C-x b` の候補           | バッファ名。最近使った順                                  |
| エコー、エラー           | バッファ名(ファイルを示すときは、`~/` で短縮した絶対パス) |
| 位置情報(エディタ連携)   | 絶対パス(プロトコルの確認と変更が要る。別項目)            |

### 9.2 表示は最小限にする【決定】

UNIX / Emacs の、切り詰めた UI の美学を尊重し、表示を増やさない。

- モードラインの名前は、バッファ名だけ(ディレクトリも、アンカーも添えない)。`C-x b` の候補も、バッファ名だけ。
- 場所が分からなくなったときは、Emacs と同じく、`C-x C-f` を押して確かめる(入力欄は、基準のディレクトリから始まる)。確かめたら `C-g` で戻る。
- そのために、ツールチップや、絶対パスを表示するコマンド(`C-h f`)は、新設しない。

## 10. 複数フレーム【決定】

Emacs の frame(macOS のウィンドウ)を複数持てる。並行する仕事ごとに、フレームを分ける使い方を想定する。

- **1 フレーム = 1 つの `NSWindow` + 1 つの WKWebView + 1 つの Web コア。** 各フレームは、自分のバッファ、最近使った順、参照履歴、window の分割、ミニバッファを持つ**独立した作業場**。JS のモデルは WebView をまたいで共有できないので、フレーム間の状態の同期はしない。
- したがって、`C-x b` の候補は、そのフレームで開いたバッファだけ。同じファイルを複数のフレームで開いてもよい(内容は、フレームごとに別々に持ち、ファイルの更新は、各フレームが検知する)。
- **切り替え:** `Cmd-1`、`Cmd-2`、`Cmd-3` … で、対応するスロット番号の**開いている**フレームを前面に出す。Window メニュー(macOS の流儀)に、開いているフレームの項目(`HyperBuf [N]`、前面のものに印)を並べ、そのショートカットとして実装する。WebView にフォーカスがあっても効く(Emacs 側のキーと衝突しない)。開いていない番号では、何も起きない(メニューにも項目がない)。専用の Frame メニューは持たない。
- **スロット番号は固定。** フレームを閉じても、他のフレームの番号は変わらない(フレーム 2 を閉じても、フレーム 3 は `Cmd-3` のまま)。新しいフレームは、空いている最小の番号を使い、`File > New Frame`(`Cmd-N`)か `C-x 5 2` で作る。
- Emacs の操作に合わせたキーを用意する: `C-x 5 2`(フレームを作る)、`C-x 5 o`(次のフレームへ)、`C-x 5 0`(このフレームを閉じる)、`C-x 5 1`(ほかのフレームを閉じる)。Web コアは、ホストの契約(`host.frames`)を通して操作する。
- **外部からの「開く」要求**(CLI、Emacs、URL スキーム)の行き先は、**最後にアクティブだったフレーム**。`--frame N` や `--new-frame` での指定は、後から足せる(今は含めない)。
- **「エディタで編集」で記録した位置**(`get-location`)と `get-view` は、記録した、または最後にアクティブだったフレームのものを返す。
- **記憶した許可パス**(§5.4)と設定は、全フレームで共有する(ホスト側で管理する)。ファイルの監視は、フレームごとに、表示中のファイルを対象にする(同じファイルを複数のフレームが表示するときは、ホスト側で重複を避ける)。

### 10.1 セッションの形式

`session.json` を、バージョン 2 にする。

```json
{
  "version": 2,
  "active": 1,
  "frames": [
    {
      "slot": 1,
      "rect": { "x": 0, "y": 0, "width": 1200, "height": 800 },
      "snapshot": { "...": "M7 の 1 フレーム分" }
    }
  ]
}
```

- `snapshot` は、M7 の `SessionSnapshot`(配置・履歴・閲覧位置・選択中の window・最近使った順・選択範囲)をそのまま使う。
- `rect` は、ウィンドウの位置と大きさ。復元時に、画面の外にならないよう、現在の画面に収まる位置に補正する。これで、これまで未決だった「ウィンドウの大きさ・位置」も保存される。
- `active` は、最後にアクティブだったフレームのスロット。
- **フレームを閉じたとき:** 最後の 1 つでなければ、そのフレームのセッションは破棄する(Emacs の `delete-frame` と同じ)。最後の 1 つを閉じる、またはアプリを終了するときは、その時点の全フレームを保存する。
- 保存は、フレームごとの遅延書き込み(M7 と同じ)を、ホストが集めて、1 つのファイルに書く。壊れたフレームは、そのフレームだけ捨て、ほかは復元する。

### 10.2 実装上の影響

- Swift: 今の `ProjectSession`(プロジェクトに結びついた 1 つの状態)は、絶対パス化で「プロジェクト」がなくなるので、`FrameSession` に置き換える。`AppModel` は、フレームの一覧(スロット → `FrameSession`)を持つ。ソケットのサーバーは 1 つで、要求を、行き先のフレームに振り分ける。
- メモリ: 段階 0 の実測([poc-frames-results.md](poc-frames-results.md))で、**フレームを 1 つ増やすごとに約 140〜150 MB 増える**(1 フレーム約 190 MB、5 フレーム約 740 MB、8 フレーム約 1.2 GB)と分かった。WebContent は、フレームごとに別々のプロセスで、共有されない。3〜5 フレームの使い方なら許容できるので、この構成を採用する。

## 14. プロジェクト・ルート(v0.1.2 の設計案)【仮】

状態: **設計案(未実装)**。合意した方針は【決定】、案のものは【仮】。

### 14.1 考え方【決定】

- Emacs の `project.el` と同じく、**プロジェクトは、バッファから求める「ルートのディレクトリ」にすぎない**。選んだり、開いたり、切り替えたりする状態は持たない。
- **フレームとの対応はない。** フレームは、独立した作業空間であって、プロジェクトに結びつかない。同じフレームに、異なるプロジェクトのバッファがあってよい。プロジェクトは、バッファを通してだけ、フレームと関わる。
- したがって、保存するもの(セッション、設定)に、プロジェクトは現れない。ルートは、そのつど、バッファのファイルのパスから計算する。

### 14.2 ルートの求め方【決定】

バッファの基準のディレクトリ(§2)から、親へさかのぼり、**最初に VCS の目印があるディレクトリ**を、ルートにする。

1. 目印: `.git`(ディレクトリ、またはファイル。worktree・submodule)、`.hg`、`.svn`、`.bzr`、`_darcs`、`.jj`。【仮: 目印の一覧】
2. さかのぼりは、**`~` と `/` に達したら止める**(その手前までで、目印がなければ、見つからなかったことにする)。`~` 自体が dotfiles のリポジトリでも、ホスト全体がルートにならない。基準のディレクトリが `~` や `/` 自身のときも、同じく見つからなかったことにする。
3. 次の「無視リスト」(§14.3)にあるディレクトリは、目印があっても、ルートにしない(飛ばして、さらに上へ)。
4. **見つからなかったときは、基準のディレクトリ自身をルートにする。** `~/Downloads/notes/` のように、フォルダを切っただけで VCS がない場所でも、その中を一覧・検索できる。
5. §4 の守り(`~` と `/` は再帰の起点にしない。件数・時間の上限、`C-g`、タイムアウト)は、**ルートに対しても、そのまま適用する**。たとえば `~` が基準でルートになったときは、1 階層の一覧にして、そう知らせる。

仮想バッファのルートは、その基準のディレクトリ(§2)から、同じ規則で求める。

### 14.3 無視リスト(`projectIgnorePaths`)【仮】

安全のため、**ルートにしないディレクトリ**を設定できる。

```json
{
  "projectIgnorePaths": ["~/work/wrapper"]
}
```

- 絶対パス、または `~/…` で書く。シンボリックリンクは解決して照合する。**完全一致**(そのディレクトリ自身だけ。下のディレクトリには効かない)。
- 一致したディレクトリは、目印があっても飛ばし、さらに上をさがす。最後まで見つからなければ、§14.2 の 4 のとおり、基準のディレクトリ自身になる。
- **既定は空**(`~` と `/` は、§14.2 の 2 で、組み込みで除く)。`warnPaths` と同様に、書いたら一覧全体を指定する。
- 不正な値(相対パス、型違い)は、無視して、理由を `C-h b` の「設定の問題」に出す。

### 14.4 ホストの契約【仮】

ファイルシステムを見るのは、シェル側の役割。

- `host.projectRoot(dir): Promise<string>` を加える(絶対パスで返る。見つからなければ、`dir` 自身)。Swift 側は、`HyperBufKit` に専用の型を置く(`DirectoryLister` と同様に、単体でテストできる)。
- 目印の確認は、メタデータの確認だけで、ファイルの中身は読まない(警告パスの判定は、通さない)。
- 結果は、コマンドの実行中だけ使う(キャッシュは、持たない。さかのぼりの回数は、パスの深さだけ)。

### 14.5 コマンド【仮】

| キー        | コマンド                      | 動作                                                                                                                                                           |
| ----------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `C-x p f`   | `project-find-file`(既存)     | **ルート以下**の `*.md` を再帰で一覧にする。入力に `../`、`~/`、絶対パスを打つと、起点がそのディレクトリに切り替わる(従来どおり。切り替えたあとは、さかのぼらない) |
| `C-x p g`   | `project-find-regexp`         | **ルート以下**の全文検索(結果は仮想バッファ `*search: …*`)。既存の検索(`TreeSearch`)を、起点だけ変えて使う。正規表現は未対応(§14.6)                              |
| `C-x p b`   | `project-switch-to-buffer`    | **現在のフレームのバッファのうち、現在のバッファと同じルートのもの**だけを候補にして、`C-x b` と同じように切り替える                                           |
| `C-x p k`   | `project-kill-buffers`        | 同じ範囲のバッファを、まとめて閉じる。**閉じる件数を示して、確認する**(`y/n`)                                                                                 |
| `C-x p d`   | `project-find-dir`            | ルート以下のディレクトリを選んで、その中で `C-x C-f` の入力欄を開く。【検討: v0.1.2 に入れるか】                                                              |

- 入力欄のプロンプトに、ルート(`~/` 形式に短縮)を示す。例: `Find file in ~/work/foo/: `。
- **作らないもの:** `C-x p p`(`project-switch-project`)と `C-x p K`(`project-forget-project`)。切り替える状態がなく、編集の作業もしないため、価値が小さい。`C-x p r`(置換)、`C-x p c`(コンパイル)、`C-x p s` / `C-x p e` / `C-x p !` / `C-x p &`(シェル)、`C-x p v`(VC)、`C-x p D`(Dired)も、閲覧専用・外部コマンドの非実行の方針により、作らない。`C-x p F` / `C-x p G`(外部も含む)は、`C-x p f` が外部のディレクトリへ届くので不要。
- キーは、既存の `keybindings` 設定(個別の割り当て)で変えられる。`C-x p` 専用の仕組みは、持たない。

### 14.6 全文検索との関係【仮】

- `M-s g`(`search-project`)は、**今までどおり、基準のディレクトリ以下**にする。`C-x p g` は、**ルート以下**にする。範囲の狭い検索と広い検索の、両方をキーで選べる。
- 同じ実装(`host.search`)を使い、起点だけが違う。除外(隠しファイル、`node_modules`)・上限・打ち切りは、共通。
- 正規表現と `.gitignore` の解釈は、今までどおり未対応(§4、`TreeSearch` の注記)。`project-find-regexp` という名前だが、v0.1.2 では固定の文字列の検索であることを、`M-x` の説明に書く。

### 14.7 バッファごとのルート【仮】

- バッファに、ルートを保存しない。必要なとき、バッファのパスから求める(ファイルが移動・削除された場合も、パスの親を見る)。
- `C-x p b` / `C-x p k` の「同じルート」は、各バッファのルートを求めて比べる。バッファの数は少ないので、コストは問題にならない。
- **対象は、現在のフレームのバッファだけ。** HyperBuf のバッファは、フレームごとに持つ(§10)。Emacs の `project-kill-buffers` が、全フレームを見るのとは異なる。【仮】
